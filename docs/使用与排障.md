## 找不到 Conda

**权限：普通 PowerShell。** 首先检查当前窗口能否找到 Conda：

```powershell
Get-Command conda -ErrorAction SilentlyContinue
```

没有结果时，确认已安装 Conda。可打开安装器提供的 Anaconda / Miniconda PowerShell 终端，
再进入仓库目录；也可以使用自己安装目录中的 `Scripts\conda.exe`。
下面仅是路径写法示例，必须替换成实际存在的文件：

```powershell
$env:CONDA_EXE = 'D:\Tools\Miniconda3\Scripts\conda.exe'
& $env:CONDA_EXE --version
& $env:CONDA_EXE run -n msgx --no-capture-output python -s -m msgx.main gui
```

后续文档中的 `conda` 也可以替换为 `& $env:CONDA_EXE`。
此变量只影响当前 PowerShell 及其子进程，不会让已经打开的 Explorer 自动获得新配置。
若主 EXE 只有在这个窗口中才能找到 Conda，就从同一窗口执行 `& .\QQ_Message_Extraction.exe`。

**成功标志：** Conda 能输出版本，应用能够找到所选环境。找不到命令不等于缺少管理员权限。

## 权限错误

**先看错误中的具体路径和动作。** 单独一个 `Access is denied` 或 `WinError 5` 不足以确定根因。

| 错误发生在哪里 | 处理方式 |
|---|---|
| Conda 创建环境或安装依赖时 | 查看环境／缓存目录的写权限；受保护位置用有写权限的窗口，不向 `base` 或用户 site 安装来绕过 |
| 写 `.ui`、日志、数据库时 | 检查项目与数据目录权限、只读属性以及是否被其它程序占用 |
| 替换 `QQ_Message_Extraction.exe` 时 | 先正常关闭主程序；管理员权限不能替代关闭正在运行的 EXE |
| 结束或启动 NapCat / QQ 时 | 该流程涉及提权；允许应用请求的 UAC，并核对实际目标账号与安装目录 |
| 被系统或组织策略拦截时 | 保留完整错误交给维护者或管理员处理，不把关闭防护作为通用步骤 |

检查 Conda 配置的目录，**普通 PowerShell，只读**：

```powershell
conda info
conda config --show envs_dirs pkgs_dirs
```

本次本机已选环境为 `D:\Dev\Anaconda\envs\msgx`。2026-10-20 只读检查发现其父目录的普通 `Users` 组仅有读取／执行权限，
因此创建环境、安装或更新依赖应使用有写权限的窗口，通常是管理员 PowerShell；运行 GUI 无需因此整体提权。
其他协作者按自己的目录权限判断，不把这一机器的 ACL 当作所有安装的要求。

如果还没有创建环境，并决定改用自己可写的位置，先确认新目标，再为**当前窗口**设置父目录。
例如下面的两个变量只用于选择用户拥有的环境／缓存目录；不要在本次已确认目标之外顺手另建一份：

```powershell
$env:CONDA_ENVS_PATH = Join-Path $env:LOCALAPPDATA 'conda\envs'
$env:CONDA_PKGS_DIRS = Join-Path $env:LOCALAPPDATA 'conda\pkgs'
```

核对后再按 README 创建环境和安装依赖；已有有效环境不重建，不直接剪切环境文件夹。
**以后也必须让 Conda 使用相同的目录配置**，否则 `-n msgx` 可能找不到该环境。
若只设置了上述临时变量，重新打开窗口后须重新设置；从该窗口启动的 EXE 才会继承它们。
这与向用户级 `site-packages` 安装依赖不同：依赖仍装在一个明确的独立 Conda 环境内。

如果某项操作明确要求管理员 PowerShell：在开始菜单搜索 PowerShell，选择“以管理员身份运行”，
确认 UAC 后，**重新进入仓库目录，重设环境选择，再核对 `conda env list` 和真实解释器路径**，
不要默认新窗口仍在原目录或仍能找到原环境。创建时确认 Conda 显示的 `environment location`，位置不符就取消。
使用另一个管理员账号时，原用户的环境、文件权限和 Windows 凭据也可能不同。

本应用的 NapCat 操作会自行请求提权；日常打开 GUI 无需为此整体提升权限。
不要把开发工具沙箱的执行授权，混同为 Windows 用户必须使用管理员 PowerShell。

## 自定义环境名

默认名为 `msgx`。若本项目使用独立环境 `msgx-dev`，在源码、测试、构建或 EXE 入口前统一设置：

```powershell
$env:CONDA_ENVS_PATH = 'D:\Dev\Anaconda\envs' # 换成已经确认的环境父目录
$env:MSGX_CONDA_ENV = 'msgx-dev'
conda run -n msgx-dev --no-capture-output python -s -m msgx.main gui
```

所有安装和运行命令中的 `-n msgx` 也要改为 `-n msgx-dev`。
环境名只使用英文字母、数字、点、下划线和连字符，首字符为字母或数字；
不能是 `base`、`root` 或目录路径。

从设置变量的同一 PowerShell 启动已有 EXE：

```powershell
& .\QQ_Message_Extraction.exe
```

不要在 PowerShell 中设置临时变量后，又转到已有 Explorer 窗口双击，误以为它会继承刚设置的变量。
程序会核对实际 Python 与选定 Conda 环境；不匹配时拒绝运行，不借用旧 `.venv` 或全局 Python。

## 配置保存位置

| 内容 | 保存位置 | 生效方式 |
|---|---|---|
| 团队默认参数 | `config.yaml` | 由 Git 管理，不填个人路径或秘密 |
| 可选本机主配置 | `.ui/config.local.yaml` | 完整替代共享主配置；改后重开 GUI 和服务 |
| 本机目标 QQ、路径、过滤等设置 | `.ui/preferences.yaml` | 界面保存，按提示重启服务 |
| API 密钥 | 当前 Windows 用户的凭据管理器 | 保存成功后供相应配置使用 |
| API 公开参数导入／导出 | `.yaml` 文件 | 在设置页导入并保存，不包含密钥 |
| 关键词列表 | 本机偏好 | 保存后按新规则查询，无需重启服务 |
| 阅读状态、重点、心得 | 本地数据库 | 保存后保留，历史报告原文不改写 |

API 配置的格式示例见 [api-config.example.yaml](api-config.example.yaml)。
应用不自动加载 `.env`。不要把密钥、平台登录令牌或个人路径写进共享配置。

### 本机端口、Token 与数据路径

需要修改 `onebot` 端口／Token、`app` 数据路径等非 GUI 字段时，先复制一份完整主配置。
**仓库根目录、普通 PowerShell，仅首次需要这些参数时执行；已有本机文件不覆盖：**

```powershell
if (Test-Path -LiteralPath '.ui\config.local.yaml') { throw '本机配置已存在，请直接编辑，勿覆盖。' }
New-Item -ItemType Directory -Path '.ui' -Force | Out-Null
Copy-Item -LiteralPath 'config.yaml' -Destination '.ui\config.local.yaml'
```

**成功标志：** `.ui/config.local.yaml` 存在，共享 `config.yaml` 未改动。
编辑新文件所需字段；API 密钥仍通过界面保存到凭据管理器。`.ui/` 不进入 Git，但 OneBot Token 仍需作为本机秘密保管。
相对数据路径以项目数据根为基准（默认仓库根），不是以 `.ui/` 为基准；改路径不会迁移旧数据。

加载顺序是：**显式 `--config` → 默认数据根下的 `.ui/config.local.yaml` → `config.yaml`**，三者选一。
本机文件与共享文件不逐字段合并；选中文件未写的字段使用程序内置默认值，建议从完整共享文件复制后维护。
随后再叠加界面偏好；因此 GUI 已保存的同名设置优先于主配置。更新共享默认值不会覆盖已有个人文件。
GUI、主 EXE 和后台都使用这条主配置选择规则；本机 YAML 解析失败时会报错，不悄悄忽略它。
临时指定另一份完整配置时，参数放在子命令前，**普通 PowerShell、仓库根目录**：

```powershell
conda run -n msgx --no-capture-output python -s -m msgx.main --config '.ui\config.local.yaml' gui
```

预期使用所指定的主配置打开界面；此命令只展示显式选择方式，正常情况下无须重复传默认本机文件。

YAML 用空格缩进；账号和群号加引号，Windows 路径用单引号，多行提示词可用 `|`。
不要把旧版 TOML 的 `[llm]` 等段落写法复制进 YAML。
不同设置的空值含义不同：提示词留空可沿用默认，关键词清空可关闭关键词匹配，发言人名单清空表示不过滤发言人。

### 命令行后台服务与界面偏好

GUI 启动后台时会传入 `MSGX_PREFS`。直接执行 `run` 不会自动加载界面的本机偏好。
确需无界面运行，并使用已保存的本机偏好时，在**普通 PowerShell、仓库根目录**执行：

```powershell
$env:MSGX_PREFS = (Resolve-Path -LiteralPath '.ui\preferences.yaml').Path
conda run -n msgx --no-capture-output python -s -m msgx.main run
```

前提是偏好文件已由界面保存，并且没有另一个接收服务占用相同端口。
不需要界面偏好时，在新窗口直接运行 `run`，或先清除当前窗口的 `MSGX_PREFS`。
命令行服务可用 Ctrl+C 正常退出；不要同时从 GUI 再启动一份。

## 手动验收与恢复个人设置

下面是用户亲自验收的操作路线。若已另行授权 Agent 创建环境和安装，应记录其实际结果；用户仍需验收启动与配置，不能把 Agent 的安装、静态检查或历史记录当作亲自完成了干净安装。
每一步保留执行命令、退出结果和看到的状态；失败时只反馈命令、完整错误、目录与权限，隐藏账号、密钥和聊天内容。

### A．干净安装

1. **准备新克隆。** 从已提交的版本克隆到新目录，不复制 `.ui/`、`data/` 或旧 EXE。
   本机可选择 `D:\Dev\MCP\msgx-install-check`；其他协作者选择自己可写的新目录。原项目照常保留，不为了验收删除旧环境或停止在用程序。
2. **确认环境。** 先确认尚未使用的环境名称和目标目录，再按 README 创建并安装；同步替换命令中的环境名、父目录和 `MSGX_CONDA_ENV`。
   如果目标已经是一个使用中的环境，先停止本次干净安装路线并确认新方案，不能覆盖或把复用旧环境记为干净安装。
   `-e .` 会把该环境关联到新克隆，不能用运行中原项目的环境来做这一步。
3. **排除继承的旧路径。** 在新克隆根目录的当前 PowerShell 清除以下进程变量，只影响当前窗口及之后的子进程，不改系统设置或正在运行的应用：

   ```powershell
   Remove-Item Env:MSGX_ROOT, Env:MSGX_PREFS, Env:PYTHONPATH -ErrorAction SilentlyContinue
   ```

   **预期：** 后续入口按当前源码定位根目录，不读被这些变量指向的旧偏好。若你有意使用其他数据根，本路线先不要设置它。
4. **核对来源。** 按 README 检查实际解释器、两个环境前缀、用户 site、依赖路径及 `msgx.__file__`。
   Python／依赖必须来自目标环境，源码必须来自新克隆；仅看到终端 `(base)` 或环境名 `msgx` 不能判断应用归属。
5. **只打开界面。** 先用源码命令确认可见“待配置”状态和空消息，再正常关闭。此步不启动接收服务、不登录或重启 NapCat、不调用模型。
   同一 Windows 用户仍可能读到原有 API 凭据；新目录不是凭据隔离边界，不要以“没复制配置”推断“肯定没有密钥”。
6. **按需验证 EXE 和业务。** 可选 EXE 由用户按 README 构建，从同一已设置环境变量的窗口运行。
   后续填写自己的账号和路径后，再单独安排后台、连接及新消息验收；如果原服务还在占用端口，不启动第二份争用同一账号／端口。

成功记录分层填写：**窗口打开 → 后台就绪 → 协议已连接 → 目标账号新消息到达**。
模型保存成功与真实生成成功另外记录，不为通过安装验收默认发送付费请求。

### B．原位置升级与设置保留

1. 保留原 Conda 环境、仓库路径和数据路径，由用户正常停止接收服务并关闭 GUI，再更新代码。
   如果涉及备份，确认所有数据库写入者已退出，或使用一致性数据库备份；不要在运行中只复制一个 `msgx.db`。
2. 保留下表的个人资料。普通源码更新不重新创建环境、不重新填写设置；依赖声明或源码目录变化时才在选定环境重新执行 `-e .`。
3. 先打开 GUI，核对账号／路径、API 公开参数、过滤规则、关键词、图标及历史报告和批注。
   账号凭据异常先看 Windows 用户、配置标识和 API 地址，不把设置显示出来当作已连通。
4. 了解下述自动任务后，再由用户启动服务并分别验证后台、协议和消息。升级保留通过须由用户实际反馈，不能用代码检查替代。

| 应保留的内容 | 实际位置与恢复条件 |
|---|---|
| GUI 个人配置与规则 | `.ui/preferences.yaml`；含账号、路径、API 公开参数、过滤及关键词，保留完整文件 |
| 本机主配置 | `.ui/config.local.yaml`（若有）；含端口／数据路径等；使用显式 `--config` 或 `MSGX_PREFS` 时还须保留其指向的文件 |
| 自定义图标及旧启动器 | `.ui/` 内保存的图标副本与 `launcher-backups/`；原始导入图片无需保留，换目录后核对偏好路径和本地图标回退结果 |
| 聊天、摘要任务、用量、阅读批注 | 默认 `data/msgx.db`；自定义位置以主配置为准，数据库备份需要一致性 |
| 原图和报告文件 | 默认 `data/media/`、`data/reports/`；与数据库一起保留，不能仅保留报告列表 |
| 排障记录 | 默认 `data/logs/` 及原有备份；不作为源码清理目标 |
| API 密钥 | Windows 凭据管理器；同一用户、API 配置标识与地址一致时可复用；换电脑／用户通常重新输入，公开参数导出不含密钥 |
| QQ／NapCat 登录态 | 各自安装和用户目录；不能通过复制 `.ui/` 保证登录有效，必要时重新扫码 |

**恢复旧资料后启动服务可能恢复自动任务。** 服务启动约 5 秒后开始检查摘要补期；有条件时会生成漏期报告，
取回已保存的模型响应或恢复可重试任务，并重试失败的图片下载；保留策略还会清理过期消息和图片。
这些操作可能访问网络或产生模型费用。先核对 API、历史任务和保留天数，再决定是否启动；只打开 GUI 不等于同意执行这些后台任务。

**本路线不做跨数据根迁移。** 数据库内图片和报告可能存有旧的绝对路径，复制整个 `data/` 也不会自动改写。
复制库后在新目录启动服务，旧路径上的图片仍可能被保留策略清理；它不能充当安全的隔离测试副本。
需要更换资料位置时，另行核对路径迁移与恢复方案，暂时保留原位置和备份，不以删除旧目录“验证”新副本。

## NapCat 配置

本项目当前对接 Windows Shell 目录，所需文件见 README。
首次按上游说明运行 NapCat，生成 `config/webui.json` 后，再交由本应用管理重启。
WebUI 的端口和登录信息以该安装实例的配置或启动输出为准，不要把令牌发到聊天或提交 Git。

在**实际账号的** OneBot 设置中检查反向连接：

| 字段 | 值或要求 |
|---|---|
| `enable` | `true` |
| `url` | 默认 `ws://127.0.0.1:6700/onebot/ws` |
| `messagePostFormat` | `array` |
| `reportSelfMessage` | `true`，用于接收本人消息 |
| `token` | 与本项目 `onebot.access_token` 一致 |

可以通过 WebUI 修改，避免直接覆盖已有账号配置。
仅修改全局模板不一定会更新已经存在的账号配置；以实际登录账号使用的配置为准。
WebSocket 客户端和服务器是不同选项，不能把反向地址填进正向服务器配置。

“强制重启”会检查接收服务，再定向重启目标安装目录的协议端并请求新二维码。
**这一步需要 UAC 提权授权**，扫码后还要等待新群消息验证。
已有其它账号的登录状态时，应先在 NapCat 中切换到目标账号，不要靠反复重启解决账号不一致。

不要直接调用内部 `restart_napcat_target.ps1`，它需要界面生成的请求参数。
遗留 `tools/重启协议端.bat` 是全退实现，可能影响普通 QQ；日常使用界面的定向重启。
已有运行中的协议端不要再重复启动，多进程数量本身也不能证明一定存在故障。

## 实时消息与过滤

实时消息默认显示 200 条，支持群筛选和仅看图片。显示条数限制的是预览，不是数据库容量。
内容列使用已保存的 OCR 预览；单击后在“消息详情”查看全文、逐图 OCR 和已有图片语义。

| 底部页签 | 行为 |
|---|---|
| 群活跃度 | 按北京时间当天未过滤、已入库的消息计数；不受上方预览条数影响 |
| 消息详情 | 当前消息正文、图片 OCR 与已有语义 |
| 与我相关 | 本人消息以及单独 @／引用回复；含 @全体成员的消息不进入相关列表 |
| 关键词消息 | 独立检索命中消息，可翻页并随群筛选 |

本人和回复本人的消息标红；关键词命中使用黄色背景，同时命中时保留红字。
关键词支持普通文本和 `re:` 开头的正则，忽略英文大小写。例如：

```text
项目进展
re:额度|限流
re:价格\s*[:：]\s*\d+
```

匹配正文及已有 OCR／语义，不额外调用模型。无效正则会提示，保存成功后才使用新规则。
引用的原消息不在库中时，程序不能凭空确认它是否回复了本人。
NapCat 未开启本人消息上报之前的记录不会因开启设置自动补回。

### 发言人过滤与计数

默认名单包含“Q群管家”和“智能客服”，可在设置页添加、删除或清空。保存后重启服务。
按完整名称匹配；“Q群管家”还匹配已核验的账号。正文提到该名称不等于发言人命中。

- 命中的新消息直接丢弃，不入库、不做 OCR 或模型请求。
- 历史记录保留，但从当前列表、当日计数及后续原始消息摘要材料中排除；取消过滤后已有记录可恢复显示。
- 已经丢弃的新消息无法补回；已经生成的摘要不会自动改写。
- 活跃度不计已过滤的图片或表情，即使已识别或选入摘要；同一消息多张图片不重复计数。
- 过滤图片和过滤发言人不同：保留了链接的过滤图片仍可查看、OCR 和手动选入摘要。

群列表有其它账号的空群时，可先连接目标账号，再使用设置中的“只保留当前账号的群”。
该操作会修改本地群条目；先阅读界面提示，不把它当作普通刷新。

## 图片与 OCR

图片先下载并校验，在本机运行 OCR。默认不自动调用图片模型，也不默认纳入摘要。

| 操作 | 是否调用模型 |
|---|---|
| 看内容列 OCR、打开消息详情、查看原图 | 不调用 |
| 点击手动“识别” | 调用所选 API 的图片模型，可能计费 |
| 勾选“纳入摘要” | 勾选本身不调用；后续生成摘要时发送已有语义，缺少语义则使用 OCR |

识别结果保留；取消纳入摘要不删除已有 OCR／语义。已识别图片重复操作可复用成功结果。
图片识别失败后按需手动重试，不为了排障额外发送收费测试。

只有 `[图片]` 时，先看是否有原图链接、下载是否成功，再看 OCR 是否完成。
旧记录没有保存图片链接时无法补回原图；没有可识别文字的图片也可能没有 OCR 结果。
`image file is truncated` 或解码失败可能来自不完整／不支持的图片，需结合下载日志确认，不单凭一行错误认定 OCR 损坏。
依赖版本以 `pyproject.toml` 为准，不单独升级 OCR 引擎来试错。

## 自动摘要与补生成

日报读取有效原始消息及选中的图片文字；周报复用日报，月报使用月内完整周报和边界日报。
上级报告不重新解析图片，也不能恢复下级摘要已省略的细节。

- 计划采用北京时间完整自然周期，午夜会先短暂等待入库，再按日报、周报、月报顺序处理。
- 初次启用日报以昨天为起点；周、月计划以当前周／月为基线。为了生成首个月报，可能先补齐当月较早的日报和周报并产生费用。
- 服务关闭时不会生成；重启后按保存的基线处理漏期，不能把它理解为自动补齐所有历史聊天。
- 日报默认目标 3000 字，周报 2 倍、月报 3 倍；篇幅是模型目标，不保证精确字数，完整输出不会被本地硬截断。
- 提示词中的 `{{目标字数}}` 在请求时替换。修改设置影响后续任务，不自动重写已有报告。
- 上下文不足时才进行必要分块。报告 HTML 默认位于 `data/reports/`，失败的未完成正文另行保存。

“摘要全文”按报告覆盖的内容日期排序；补生成旧日报不会因为生成时间较新而排到最新内容之前。
阅读状态由用户设置，打开报告不自动标记已读；重点和心得保存在本地数据库。
周月报生成时可以使用已保存的重点和心得，后加批注不会自动重写已完成的上级报告。

### 摘要失败

先看“运行状态”的失败原因以及“消费明细”，区分连接未建立、处理中断、输出不完整和永久错误。
**未返回用量不等于免费，处理结果未知也不等于服务商没有生成。**

当前 OpenAI 官方自动摘要使用后台响应：拿到任务 ID 后继续查询同一个任务，重开后也可恢复取回。
没有可恢复 ID、结果未知或输出不完整时，任务可能暂停，等待人工核查。
该路径会向服务商保存后台响应；不要将它描述成所有请求都使用 `store=false`。

需要补做已暂停任务时，在“运行状态 → 自动日报／周报／月报”选择待处理项，再点“确认补生成”。
阅读可能重复计费的提示后决定；已有完整成稿会复用。
当前没有通用的 CLI `summary` 命令，不使用旧版接口说明来手动重发。

`ServerDisconnectedError`、`ClientPayloadError` 只描述断连或接收失败，不能直接归因于代理、OCR 或权限。
结合日志的上传、响应和任务状态判断；不要通过反复点击补生成来验证网络。

## 费用与 API 配置

设置页可新增服务商配置，选择配置后保存。参数导入／导出不含密钥；
修改 API 地址或配置标识后，要核对相应密钥是否已单独配置。
输入框出现密钥不代表已经保存，以带时间的保存结果为准。

当前官方 OpenAI 配置的服务档位默认采用 Flex，可选择 Standard；
是否支持该档位取决于实际模型及接口。程序不会因 Flex 资源不足自动改用 Standard。
费率填写 Standard 基准价，Flex 估算乘 `0.5`，避免重复减半。

消费记录保留各次请求使用的费率和汇率，不按新设置重算历史记录。
本地账目只覆盖已记录请求，未知用量单列；不能保证与服务商账号的全部消费相等。
“今日”按北京时间统计；与采用 UTC 的平台日账单比较时，使用对应的 UTC 汇总和相同币种。
预算达到已配置门槛后停止新的模型调用，消息接收继续。

旧 DeepSeek 余额／平台账单逻辑属于兼容路径，设置页已不再提供旧账单模块。
不要按旧教程寻找已移除的“平台 token”输入框，也不要把余额变化称为精确的逐请求费用。
具体模型价格、额度、保留政策以实际服务商为准，本文不维护一份会过期的价目表。

## 打不开界面

**普通 PowerShell，仓库根目录，只读检查：**

```powershell
conda env list
conda run -n msgx --no-capture-output python -s -c "import sys, site, tkinter; print(sys.executable); print(site.ENABLE_USER_SITE); print(tkinter.TkVersion)"
```

确认环境名、Python 路径与 Tk；然后用 README 的源码启动命令查看完整错误。
`ModuleNotFoundError` 指向哪个模块，就核对独立环境中的对应依赖；不要改用全局 Python 绕过。
EXE 需要与仓库源码放在一起，失败日志见 `.ui/exe_error.log` 和 `.ui/gui_error.log`。

## 服务运行但没有新消息

按顺序判断，不把“进程在运行”当作“已经收消息”：

1. **接收服务就绪吗？** 查看运行状态和服务日志。端口绑定失败时先查占用者。
2. **NapCat 连对地址了吗？** 核对实际账号、反向 WS、端口和 Token。
3. **QQ 仍登录吗？** 查看协议状态与登录提示。登录被撤销时需扫码，单纯重连 WebSocket 不足以恢复。
4. **目标群确有新消息吗？** 对照 QQ 的实际接收情况，不能仅看界面刷新时间。
5. **消息被过滤了吗？** 核对群选择、发言人和类型过滤；它们会影响列表和统计。

默认端口的检查命令，**普通 PowerShell，只读**：

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:6701/health' -TimeoutSec 5
Get-NetTCPConnection -State Listen -LocalPort 6700,6701
```

`/health` 能返回只能证明这个地址有服务响应，还要结合 PID、应用状态和新消息确认归属。
`protocol.state`、`ws_conns`、`last_protocol_message` 可辅助判断，连接条数不等于正常登录。
输出可能包含账号等本机信息，分享前先脱敏。

需要重新扫码时优先用界面操作；强制重启将请求 UAC。
不要直接结束所有 `QQ.exe`，也不要因为看见多个 QQ 子进程就认定是重复启动。

## 接收服务异常退出

GUI 在运行时，对符合恢复条件的异常退出分别等待 5、15、30 秒，最多恢复三次。
点击“停止服务”可取消；正常退出、关闭界面、启动端口错误等不触发这条恢复流程。
服务稳定运行五分钟后清零恢复次数。连续失败到上限后需查看日志再手动启动。

检查 `gui.log`、`service-output.log` 的时间和退出码，再查 `service.log` 与 `service-fault.log`。
外部强杀或底层库退出不一定有 Python 堆栈；最后一行“功能已就绪”不证明该功能导致退出。
恢复接收服务不等于重新登录 QQ，也不等于重新提交所有模型请求。

## 日志在哪里

默认位置如下；数据库路径改过时，服务日志跟随数据库同级的 `logs` 目录。

| 文件 | 用来检查 |
|---|---|
| `.ui/exe_error.log` | EXE 查找 Conda、环境与源码失败 |
| `.ui/gui_error.log` | 界面启动失败 |
| `data/logs/gui.log` | 启停操作、恢复过程、退出原因 |
| `data/logs/service.log` | 消息处理和摘要业务日志 |
| `data/logs/service-output.log` | 后台完整脱敏输出、原生库 stderr |
| `data/logs/service-fault.log` | Python 能捕获的原生故障栈 |
| `data/logs/napcat.log` | 本项目的协议端启动记录 |

界面日志下拉框可切换服务和协议端日志。NapCat 自己是否落盘由其账号配置决定，
某个日志目录为空不能单独证明协议端没有运行。
收集故障时保留发生时间、命令、退出码和相关错误片段，不公开完整私人日志或聊天数据库。

## 辅助工具的边界

### NapCat 安装检查

**普通 PowerShell，仓库根目录。** 将路径替换为自己的安装目录：

```powershell
conda run -n msgx --no-capture-output python -s tools\check_napcat_env.py --napcat 'D:\Tools\NapCat'
```

检查注册表、目录文件和全局 OneBot 配置；不会代替 WebUI 核对实际账号配置。
脚本可能在发现问题后仍以退出码 0 结束，因此要阅读检查输出。

需要端口探测时，`--probe` 后必须填写 **WS 和 HTTP 两个端口**：

```powershell
conda run -n msgx --no-capture-output python -s tools\check_napcat_env.py --napcat 'D:\Tools\NapCat' --probe 6700 6701
```

探测不改配置文件，但会创建短暂的本机连接，可能在服务日志中留下连接记录。
握手成功不等于目标 QQ 已登录，也不等于收到了真实消息。

### 不适合直接复制到日常终端的工具

| 工具 | 实际影响 |
|---|---|
| `tools/diagnose_freeze.py` | 会发送诊断探针，不能一概称为纯只读检查 |
| `tools/make_demo.py` | 生成演示数据；`--post` 会投递事件，`--reset` 会删除其目标数据库，不能对个人数据使用 |
| `tools/kill_dup_napcat.py` | 默认查看；`--yes`／`--elevate` 会结束进程，且并非界面当前的定向重启流程 |
| `tools/prune_groups.py` | 默认预览；`--apply` 会备份并修改群记录 |
| `msgx.main prune` | 按保留策略删除过期数据，不能当作健康检查 |

开发验证优先用 `tests/run_all.py` 中的隔离测试。确需这些工具时，先阅读其参数和目标路径，
为会改数据的操作准备独立测试数据；不在 README 的快速开始中混入重置或清理命令。

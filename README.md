# 消息萃取（msgx）

把指定的 QQ 群变成一份**可检索的知识流**。

实时接收 → 结构化落库 → 图片 OCR / 多模态理解 → 价值打分与分级 → 跨群热点 / 会议纪要 → 本机弹窗提醒。

> **这个项目不会发出任何消息。** 它只读不写，从设计上就去掉了「被风控」和「打扰群友」两条路径。

## 它解决什么问题

技术群里的有效信息密度很低：一天几百上千条，真正值得看的可能只有几条，但它们和闲聊、表情包、接龙混在一起。
事后想找「上周有人提到的那个显存工具叫啥」时，聊天记录已经刷得翻不到了。

本项目的做法是：

1. **全量落库**，一条不丢 —— 之后可按群、按时间、按关键词检索
2. **图片也要能搜** —— 报错截图、架构图经 OCR / 多模态转成文字入库
3. **分级打扰** —— 只有「现在不知道就会造成损失」的消息（被点名、有人回答了你之前的提问、限时机会）才强提醒；
   高价值但可以稍后看的进摘要；其余归档不打扰
4. **跨群热点 + 会议纪要** —— 同一件事散在多个群时，逐群摘要看不出「多群共鸣」，
   所以先做跨群统计再归纳；另有一份 ≤200 字的会议纪要，扫一眼就知道漏了什么

## 架构

```
QQ 群
  │  （你在群里，机器人小号也在群里）
  ▼
官方 QQ 客户端（NTQQ）
  │  NapCat 注入 QQ 进程，把消息转成 OneBot 11 协议
  ▼
NapCat ──反向 WebSocket──► 本服务 :6700/onebot/ws
  ▲                           │
  │ 启动由界面发起             ├─► 归一化 + 去重 ──► SQLite（WAL）
  │ （隐藏窗口，无 CMD 黑框）  │
  └── msgx.napcat             ├─► 图片下载 ──► OCR / 多模态 ──┐
                              │                              │
                              ├─► 规则预筛 ──► 模型复核 ◄────┘
                              │        │
                              │        ├─ P0：本机托盘强提醒
                              │        └─ P1/P2：入库待摘要
                              │
                              ├─► 周期摘要 / 日报 ──► HTML + 托盘通知
                              │
                              └─► 账单（msgx.billing）──► GET /health、/billing
                                    官方余额（API Key）→ 余额差值法得真实消费
                                    ＋ 平台逐日明细（可选，平台 token）
```

**为什么用独立的机器人小号？** 因为协议端需要注入 QQ 客户端，用主号有风险。小号只用于接收（本项目从不发消息），
主号留在群里正常使用，通过 `[watch] at_qq` 把主号加进「被点名」集合 —— 这样群里 @ 主号时才会触发强提醒。

## 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 10 / 11 | 通知走 Windows 托盘。核心逻辑跨平台，通知后端需另写 |
| Python | **>= 3.11** | 用到标准库 `tomllib`（3.10 及以下没有） |
| QQ（NTQQ） | **buildVersion >= 40768** | NapCat 的硬性要求。实测 `9.9.33-52230` 可用 |
| NapCat | `NapCat.Shell.zip` | 见下方安装步骤。**不要**用 OneKey 包 |
| DeepSeek API Key | 可选 | 不配也能跑：退化为「仅规则模式」，不生成摘要、不做模型复核 |

依赖只有 4 个直接包（`aiohttp` / `pillow` / `winotify` / `rapidocr-onnxruntime`），全部支持 pip 直接安装，
不需要 paddle、torch、Node.js。

## 快速开始

### 1. 准备环境

```powershell
# 在项目根目录执行。"py -3.13" 换成你那个带 tkinter 的解释器
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
```

`requirements.lock.txt` 是一份**实测跑通的环境快照**（22 个包，含传递依赖）。
不要用 `requirements.txt` 复现环境 —— 它只声明直接依赖，版本范围较宽。

> 如果 pip 装不上，先试默认源（很多情况下本地缓存里就有全部 wheel）；
> 换国内镜像出问题时优先怀疑镜像本身，而不是网络。

### 2. 配置 API Key

```powershell
# 方式一：环境变量（推荐，重启终端后生效）
setx DEEPSEEK_API_KEY "sk-你的key"

# 方式二：复制 .env.example 为 .env 并填写（需自行加载该文件）
```

不配置也能启动，只是不会生成摘要。

### 3. 启动服务

**日常用法（推荐）**：双击项目根目录的 **`消息萃取.exe`** —— 会打开图形界面，点「启动服务」即可。
不需要记命令，也不需要先配环境变量。

命令行方式（排查问题时用）：

```powershell
# 在项目根目录执行
.venv\Scripts\python.exe -m msgx.main run
```

看到这样的横幅就是成功了：


> **不要重复启动。** 端口 6700 已被占用时，第二次启动会失败并提示
> 「端口无法绑定 —— 最常见的原因：已经有一个服务实例在运行」。
> 判断方法：浏览器打开 `http://127.0.0.1:6701/health`，能返回 JSON 就说明服务已在运行。

## 安装 QQ 与 NapCat

这一步是整套流程里最容易卡住的地方，请按顺序来。

### 4.1 安装 QQ（NTQQ）

```powershell
winget install --id Tencent.QQ.NT -e
```

装完后确认版本：

```powershell
winget list --id Tencent.QQ.NT
```

也可从官网下载：<https://im.qq.com/pcqq/index.shtml>

> **注意**：`winget` 不一定装到默认目录（实测此机器装在了 `D:\App\QQ\`）。
> 不要猜路径，用 `winget list` 看版本即可；NapCat 会自己从注册表找 QQ。

### 4.2 下载 NapCat

从 GitHub Releases 下载 **`NapCat.Shell.zip`**：

<https://github.com/NapNeko/NapCatQQ/releases/latest>

| 包名 | 大小 | 说明 |
|---|---|---|
| **`NapCat.Shell.zip`** | ~29 MB | ✅ **用这个**。不需要额外装 Node.js |
| `NapCat.Shell.Windows.Node.zip` | ~117 MB | 自带 Node.js，没有 Node 环境时用 |
| `NapCat.Framework.zip` | ~30 MB | 需要另装 QQ 且走另一套注入方式 |
| `NapCat.Shell.Windows.OneKey.zip` | ~1 MB | ❌ **不要用**。这是个下载器，内部硬编码的下载域名已失效，必然报 404 |

解压到任意目录，例如 `D:\App\NapCat\`。解压后必须能看到这些文件：

```
NapCatWinBootMain.exe     ← 启动器实际调用的是它
NapCatWinBootHook.dll
launcher.bat
napcat.mjs
qqnt.json
```

如果缺文件，说明解压不完整，重新解压一次。

### 4.3 启动 NapCat

> ⚠️ **不要直接右键 `launcher.bat` 选「以管理员身份运行」。**
>
> `launcher.bat` 全程用 `%cd%`（当前工作目录）而不是 `%~dp0`（脚本所在目录）来推导路径。
> 右键管理员运行时，工作目录是 `C:\Windows\System32`，于是它去找
> `System32\NapCatWinBootMain.exe`，找不到就退出 —— 表现就是**窗口一闪而过**。

正确做法是先从注册表读出 QQ 的安装位置，再切到 NapCat 目录启动。本仓库提供了现成的包装脚本：

```cmd
tools\start_napcat.bat
```

它会：修正工作目录 → 自提权 → 自检关键文件 → 调用 `launcher.bat` → 出错时保留窗口以便截图。
**这条路径会留下一个命令行窗口**，是刻意保留的「看得见」模式，专供排障。

> **日常使用不用走这条。** 双击 `消息萃取.exe`，在界面里点「启动协议端(NapCat)」即可 ——
> 默认**隐藏控制台窗口**，任务栏里不会留下黑框（这是 v0.5.0 专门解决的）。
> 它需要 `config.toml` 里配好 `[napcat] dir`；启动前会在 Python 侧先做预检
> （关键文件是否齐全、QQ.exe 能否从注册表推导出来），不合格就直接报错，
> 不会像批处理那样静默挂死。想看完整输出就在设置页取消勾选「隐藏控制台窗口启动」。

启动成功后：

- 会弹出 QQ 登录界面 / 二维码（**用小号扫码登录**）；界面会自动把二维码弹出来
- WebUI 地址：<http://127.0.0.1:6099/webui/>
  登录 Token 在启动日志里，形如 `[WebUi] Login Token is xxxxxxxx`

### 4.4 让 NapCat 连上本服务

**推荐：预置配置，登录后自动连上，不用手点 WebUI。**

编辑 `NapCat目录\config\onebot11.json`（若文件不存在就新建；账号首次登录时 NapCat 会用它作全局模板）：

```json
{
  "network": {
    "httpServers": [],
    "httpSseServers": [],
    "httpClients": [],
    "websocketServers": [],
    "websocketClients": [
      {
        "name": "msgx",
        "enable": true,
        "url": "ws://127.0.0.1:6700/onebot/ws",
        "messagePostFormat": "array",
        "reportSelfMessage": false,
        "reconnectInterval": 5000,
        "token": "",
        "debug": false,
        "heartInterval": 30000,
        "verifyCertificate": true
      }
    ],
    "plugins": []
  },
  "musicSignUrl": "",
  "enableLocalFile2Url": false,
  "parseMultMsg": false,
  "imageDownloadProxy": "",
  "timeout": {
    "baseTimeout": 10000,
    "uploadSpeedKBps": 256,
    "downloadSpeedKBps": 256,
    "maxTimeout": 1800000
  }
}
```

> **路径必须是 `/onebot/ws`，不能写成 `/onebot`。**
> 本服务的 `/onebot/ws` 是 WebSocket 端点，`/onebot` 是 HTTP POST 上报端点。
> 写错会在第一次握手就失败（实测返回 HTTP 405）。

连上后，服务端窗口会出现：

```
INFO  msgx.onebot   协议端已连接: 127.0.0.1
```

## 配置

所有配置在 `config.toml`，改完重启服务生效。**没有配置的项会用内置默认值**，所以你可以只写需要覆盖的部分。

### 最常改的几项

```toml
[watch]
# 留空 = 处理机器人小号加入的全部群
groups = []
# 你的主号 QQ —— 群里 @ 你时才会触发强提醒
at_qq = ["你的主号QQ"]
# 群号 → 群名（群消息事件不带群名，补上便于阅读）
[watch.names]
123456789 = "某个技术群"

[summary]
interval_minutes = 30      # 多久生成一次摘要

[score]
keywords = ["招聘", "内推", "开源", "踩坑", "论文", "数据集", "复现"]
p0_min_score = 8           # 强提醒门槛，先设高避免误报疲劳
llm_review_min_score = 2   # 规则分达到多少才交给模型复核（直接决定 API 成本）
```

> `[watch] at_qq` **一定要填**。监听用的是小号，别人不会 @ 它；
> 不填的话「被点名」这条硬规则永远不会触发。

### 成本

按 DeepSeek 官方价目表（`deepseek-flash`，2026-09-10 起生效）本地估算：

| 项目 | 空闲时段 | 高峰时段 |
|---|---|---|
| 输入 · 缓存命中 | ¥0.02 / M tok | ¥0.04 / M tok |
| 输入 · 未命中 | ¥1.00 / M tok | ¥2.00 / M tok |
| 输出 | ¥4.00 / M tok | ¥8.00 / M tok |

高峰时段为 UTC 周一至周五 `01:00-04:00` 与 `06:00-10:00`（北京时间工作日
09:00-12:00、14:00-18:00）；**周末全天按空闲计价**。倍数与时段都在 `config.toml`
的 `[llm]` 里（`peak_multiplier` / `peak_windows_utc`），官方调价时改这几行即可。

- 一次 26 条消息的摘要 ≈ ¥0.003
- 单条消息的模型复核 ≈ ¥0.0014
- 5~10 个群、日均 3000~10000 条消息 ≈ **¥3/天**

`max_daily_cost_cny` 默认 10 元，超出后自动降级为「仅规则」模式，不会失控。

> **口径说明（v0.5.1 更新）**：界面上「今日花费 / 累计花费」有**三档来源**，
> 每档都会如实标注，不会混着糊弄：
>
> | 界面标注 | 数据从哪来 | 需要配什么 | 特点 |
> |---|---|---|---|
> | `（平台）` | DeepSeek 平台逐日消费明细 | 平台登录态 `userToken` | 最全，能到「逐模型」；token 短期有效 |
> | `（余额差值）` | **官方余额的下降量累加** | **什么都不用配** | 真实，但分辨率只到 ¥0.01、只给总额 |
> | `（估算）` | 官方价目表 × 本地 token 用量 | 什么都不用配 | 兜底；天然偏低 |
>
> **余额差值法（v0.5.1 新增，日常就看这个）** —— 官方 `GET /user/balance` 给的是
> **实时余额**，而账号里唯一让钱变少的事就是消费，所以「所有下降量之和」就是真实消费。
> 程序每次查余额时顺手把读数存下来（**不额外发请求**），相邻读数一减即得：
> 下降 = 消费，上升 = 充值（单记，不算消费）。**不需要 API Key 之外的任何凭据。**
>
> 它有三个诚实的边界，界面都会标出来：
> 1. **分辨率 ¥0.01**（余额只有两位小数）。日消费 ¥0.5 以上时误差约 2%；
>    某天只花几分钱时，差值就是噪声 —— 那种情况界面仍标「余额差值」，不冒充「平台」
> 2. **首次安装的那一天，「今日」会回落到估算**，并显示「自 HH:MM 起」。
>    因为读数是从启动那一刻才开始记的、只覆盖了半天，直接报出来会是个明显偏小的数
>    （用户会以为程序坏了）。**过了当晚 00:00，今日就自动变成真实值**
> 3. **累计值可能标成「（差值+估算）」**：差值只覆盖读数起始日之后，
>    更早的历史用估算补齐。刚装的那天「累计」不会显示 ¥0.00
>
> 需要「哪个模型花了多少」这种逐模型明细时，才需要配平台 token：把浏览器登录态
> 填到 `[billing] platform_token`（或界面设置页）—— 取法：浏览器登录
> platform.deepseek.com → F12 → Application → Local Storage → 复制 `userToken` 的值。
> token 只存在本机 `.ui/preferences.json`，不会进 Git。
>
> **两套凭证互不通用**（这点最容易搞混）：API Key（`sk-…`）只能查**余额**；
> 消费明细只有平台登录态能查。用 API Key 打用量接口会返回
> `code=40003 Authorization Failed`。所以本项目的策略是：**余额用 API Key 自动查，
> 消费从余额差值推**——两者都不需要你额外做任何事。
>
> 本地估算天然偏低，原因是**重试后实际被服务端处理、但我们没拿到响应体的那些请求
> 无法计数**（见「图片语义提取」一节的连接抖动）。这就是为什么 v0.5.1 要用差值法
> 取而代之。

**务必注意**：该模型默认开启思考模式，思考 token 与正文共用 `max_tokens` 且按输出价计费。
本项目对「摘要、图片描述」这类忠实提取任务已显式关闭思考（`think=False`），
实测同一任务从 1500 token 降到 34 token —— 约 **9 倍**差距。改动 `llm.py` 时不要把这个开关去掉。

> **需要思考的任务（打分、复核）必须给足预算**（v0.5.1 修）：思考与正文共用 `max_tokens`，
> 预算给小了会「思考吃光额度 → 正文为空」——这是最危险的**静默空结果**。实测思考量在
> 0~290 token 之间波动，而早期打分只给了 400，余量只剩 110。现在 `think=True` 时
> 预算会被抬到下限 `THINK_MIN_TOKENS = 1200`（可配 `[llm] think_min_tokens`）；
> `max_tokens` 只是上限，抬高了**不额外花钱**。若仍被截断且正文为空，会自动放大到 4 倍
> 重试一次，再空则记 error —— **绝不静默返回空**。

> 重新打包的命令见本节末尾。

### 运行状态

- **状态卡片**（两列并排）：
  - 左列：服务进程 / 已入库消息 / **今日花费** / 账户余额
  - 右列：协议端（NapCat）连接 / 图片语义失败 / **累计花费** / 模型状态
  - 「今日花费」右边紧挨着「累计花费」—— 两个都是**钱**，必须能一眼对比。
    每个金额都带**口径标注**：`（平台）` = 平台逐日明细、`（余额差值）` = 官方余额
    下降量推算的真实值（默认就有，无需配置）、`（估算）` = 本地按 token 用量算的兜底值、
    `（差值+估算）` = 累计里「读数起点之前」那一段用估算补齐。**今日与累计各自标各的**，
    可能一个是真实、一个是估算。拿不到的原因会写在底部状态栏
    （**绝不把估算值伪装成真实值**）。
    今日用差值口径但读数起点不是 00:00 时，会显示「自 HH:MM 起」（首次安装那天就是如此；
    过了午夜自动变成完整一天）。
  - 「协议端」一项会明确区分 *服务在跑* 和 *NapCat 已连上* —— 这两件事经常被混淆，
    是排查「为什么没有消息」时最先要看的地方。未连接时会直接提示点哪个按钮
  - 「图片语义失败」显示有多少张图的模型读图失败了。失败会自动补跑（最多 3 次），
    括号里会说明还有多少张在排队补跑
- **按钮**：
  - **「生成最新摘要」= 增量纪要**：接着**上次已经总结过**的消息继续，跨群合并成一份
    600~1500 字的会议纪要（字数随窗口长度，见下）。游标独立，不会和热点、各群摘要重复
  - **「按范围重做」**：下拉选 **最近 1 天 / 3 天 / 7 天 / 1 个月**，把那段窗口的消息
    重新总结一份。下拉框旁边会实时显示该范围的目标字数与数据来源窗口。
    不受「每群 ≥8 条」等门槛限制 —— 只要窗口内有入库消息就一定有产出
  - **「刷新群列表」** 会让服务经反向 WS 向协议端要一次真实群名（失败才退回本地库）
  - **「启动协议端(NapCat)」** 一键拉起 NapCat（QQ 会一并起来），**默认隐藏控制台窗口**，
    任务栏里不会再留下黑框。**会弹一次 UAC，必须点「是」** —— 向 QQ 进程注入 DLL
    属于管理员操作，绕不过去；但 UAC 是对话框，不占任务栏。
    想看完整启动输出时，在设置页取消勾选「隐藏控制台窗口启动」，
    或直接双击 `tools\start_napcat.bat`（那条路径刻意保留，带自检 + pause，专供排障）。
    需要配置 `[napcat] dir`（能定位到 launcher.bat 才能隐藏启动）
  - **「协议端日志」** 查看启动记录（含启动前预检：关键文件是否齐全、QQ.exe 从注册表
    推导到的路径）+ NapCat 自身日志的尾部
  - **「刷新账单」** 让服务立刻去 DeepSeek 抓一次真实余额与消费
  - **「需要登录时，二维码会自动弹出来给你扫」**。NapCat 把登录码写到它的
    `cache/qrcode.png` 就完事了，从不负责展示 —— 界面会盯着那个目录，
    出现即弹窗，登录成功后自动关闭。需配置 `[napcat] dir`。
- **日志**：服务进程的实时输出，等同于控制台里看到的内容

> 服务与协议端是**两个独立进程**：本服务只负责监听协议端连入，不负责启动它
> （OneBot 11 反向 WebSocket 的职责划分）。所以「服务在跑」不等于「能收到消息」。

### 实时消息

第三个标签页，显示**最近入库的消息**（新的在最上面）：

- 列：时间 / 群 / 发言人 / 内容 / 图片状态
- 被 @ 的行标红，图片语义失败的行标橙 —— 扫一眼就知道有没有要立刻处理的
- 纯图片消息的正文原本只是 `[图片]` 占位符，这里会剥掉占位符、
  把图片的语义或 OCR 结果顶上来
- 每 3 秒自动刷新（可关闭），**只在切到该页时才拉数据**，后台页不会浪费请求

这一页是为了替代「盯着 NapCat 那个 CMD 窗口看消息到底进没进来」——
看得见的是入库后的真实内容，比协议端滚屏有用得多。

### 跨群热点

每轮周期先出一份**跨群热点**，再出各群摘要，通知也以热点为主。

同一个话题散在多个群里时，逐群摘要永远体现不出「多群共鸣」—— 这是最容易漏掉的信号
（典型例子：某件事在几个群被分别提过，但因为没有汇总，一直没被注意到）。
所以**重复度由确定性统计算出，不交给模型去发现**：

- 候选词：`score.keywords` ∪ 技术术语（环境变量 / 命令 / 包名）∪ 中英 n-gram
- 热度 = **群数 × 人数 × log(1 + 次数)** —— 群数与人数是整数乘法，权重远高于次数，
  **「跨群 + 多人」才是真信号**，单人在单群刷屏不算
- 硬性门槛：至少跨 2 个群 **且** 2 个不同的人
- 同句碎片（「智了」「模型」这类渣滓，支持集覆盖率 ≥80%）并入最热词，不占榜

报告里每条热点都标注「N 群 · M 人 · K 次」，**密度就是排序依据**。
统计部分零成本、零新增依赖（实现见 `src/msgx/hotspot.py`）。

点「停止服务」时不会强杀进程，而是发一个信号文件让服务自己收尾退出 ——
这样不会打断正在写数据库或下载图片的动作。

### 群消息纪要（默认摘要形态）

「生成最新摘要」产出的是**会议纪要**，不是信息浓缩：一段连贯的话、**有明确字数上限**，
写「发生了什么、结论是什么」，**不分条、不按话题分类**。目标是「扫一眼就知道漏了什么」。

- **增量**（默认）：游标走独立的 `kind='digest'` 轨道，每次只总结上次之后的新消息；
  与热点轨道、各群周期摘要轨道互不干扰，不会重复总结同一批
- **按范围**：下拉选 最近 1 天 / 3 天 / 7 天 / 1 个月，把该窗口重做一份
- **字数随窗口变化**（不再写死 200 字）：

  | 范围 | 目标字数 |
  |---|---|
  | 最近 1 天 | 800 字 |
  | 最近 3 天 | 1100 字 |
  | 最近 7 天 | 1300 字 |
  | 最近 1 个月 | 1500 字 |

  窗口越长允许写越长；增量默认 800 字。上限与档位在
  `src/msgx/summarize.py` 的 `DIGEST_RANGES` 里，改一处即可。
- **长度不靠提示词保证**：实测模型会无视「不超过 N 字」写到 350~700 字。
  因此有一道确定性收敛链 —— 分层合并 →（最多两轮）压缩 → 句子边界硬截断，
  无论模型怎么答，产物都不会超过目标字数（契约由 `tests/test_digest.py` 锁死，
  覆盖 800 与 1500 两种口径）

### 图片语义提取

图片会先下载（校验完整性、去重），再本地 OCR，最后交给多模态模型做语义理解。
这一步很容易被本机到 `api.deepseek.com` 的**偶发连接抖动**（本地代理撤连接，
约 1/8 概率、与图片大小无关）打断，所以做了三层保护：

1. **上传前压图**：请求里带的是 `detail: "low"`，服务端本来就会把图缩到很低分辨率
   （实测 2.8MB 的图只计 198 个 prompt token）。客户端先缩到长边 1280 / JPEG q85，
   实测 2.8MB → 约 90KB（1/30），图像内容与提取质量无可感知差异。
2. **HTTP 层自动重试**（默认 4 次，`[llm] post_retries`）：区分「值得重试」（连接被掐 /
   429 / 5xx）与「重试白费」（4xx）。**连接从不复用**
   （`TCPConnector(force_close=True)`）—— 每次都新建连接，从根上没有「半死连接」，
   实测只多 23ms。
3. **失败会记下来并自动补跑**：`vision_state` 是独立的状态列，失败的行由媒体循环
   在空闲轮里补跑（每 ≈60 秒一批，避免网络恢复后并发轰炸模型），**补跑成功后会重新
   打分**（报错截图的识别文本正是打分依据）。补跑次数上限 3 次 —— 没有这个上限，
   一张永远读不出来的图会被每一轮反复送去推理，安静地烧钱。

界面上「图片语义失败」会显示还剩多少张在排队补跑，`data/msgx.db` 的
`messages.vision_state` / `vision_tries` 可查明细。

### 设置

| 界面项 | 作用 | 落到哪里 |
|---|---|---|
| 关注关键词 | 命中即进入候选池，再由模型判定是否值得提醒 | `score.keywords` |
| 摘要间隔 | 每 N 分钟生成一次摘要（0 = 沿用 `config.toml`） | `summary.interval_minutes` |
| 统计哪些群 | 勾选参与统计的群；**不选 = 全部群** | `watch.groups` |
| 不接收的消息类型 | 纯表情 / 纯图片 / 合并转发 / 语音 / 短于 N 字 | `filters` |
| 隐藏控制台窗口启动 | 启动协议端时不出现 CMD 窗口（取消勾选 = 可见排障模式） | `napcat.hidden` |
| 平台 token | DeepSeek 平台登录态，用于抓**逐模型**消费明细（**留空也不影响**：今日/累计仍由余额差值法给出真实值） | `billing.platform_token` |

设置页是**可滚动**的：窗口在小屏上被压扁时，滚轮（或拖动右侧滚动条）即可看到底部的
「保存设置」，不需要把窗口拉大。

**设置保存在 `.ui/preferences.json`（本人本地，不入版本库），界面永远不会改写 `config.toml`。**
这样配置文件的改动归版本管理，各人的偏好互不干扰 —— 多人协作时不会因为谁改了配置而互相覆盖。

规则是「留空 = 沿用 `config.toml`」而不是「清空」：比如关键词留空，服务仍会用配置文件里的关键词。

> ⚠️ **注意**：这些设置只在**从图形界面启动服务**时生效（界面通过环境变量 `MSGX_PREFS` 传给服务进程）。
> 若改用 `tools\启动服务.bat` 或命令行手动启动，服务只读 `config.toml`，**界面里的设置不会生效**。

### 重新打包 `消息萃取.exe`

只在 `tools\exe_main.py` 本身需要改动时才要重打包（业务代码改动不需要）：

```powershell
.venv\Scripts\python.exe -m PyInstaller --onefile --noconsole `
  --name msgx_launcher --distpath . --workpath build\tmp --specpath build `
  --paths src tools\exe_main.py
# 然后把生成的 msgx_launcher.exe 改名为 消息萃取.exe
```

> 「不选任何群」和「选了全部群」效果相同，都表示关注全部群。

## 协同开发

### 分支与提交

- 主分支 `main`，始终保持可运行
- 功能开发开 `feat/xxx`，修复开 `fix/xxx`
- 提交信息：`<类型>: <中文简述>`（如 `fix: 修复接入队列未被消费导致消息丢失`）
- 合并前请确认 `python -m msgx.main stats` 能正常跑

### 发版

1. 改 `src/msgx/__init__.py` 的 `__version__`
2. 更新 `CHANGELOG.md`
3. `git commit -m "vX.Y.Z: 简述"`
4. `git tag vX.Y.Z`

### 改代码前请先读

- `CHANGELOG.md` 的「修复」一节 —— 里面每一条都是**真实踩过的坑**，且都写了为什么要这么改。
  这些代码看起来可能「多余」，但删掉会重现 bug。
- 尤其注意这几处，它们的注释解释了「为什么不那样写」：
  - `llm.py` 的 `think=False` 与放大重试 —— 关系到成本与空摘要
  - `models.py` 的 `mface` 分支 —— 表情包也带图片 URL
  - `summarize.py` 的 `md_to_html` —— 必须先切片再转义
  - `summarize.py` 的 `_fit_length` / `_merge_all` —— 纪要不是自然就短的，
    长度由**确定性收敛**保证，删掉这层会立刻退化回几百字
  - `store.py` 的 `insert_message` —— 必须无条件注册群

### 不要提交

`.gitignore` 已覆盖：`data/`（含真实聊天记录）、`.venv/`、`.env`、`.ui/`、`_install/`、
`消息萃取.exe`（构建产物）与 `build/`（PyInstaller 中间文件）。

**提交前务必确认 `data/` 没有被加入** —— 里面有真实群聊内容。

## 排障

### 双击 `消息萃取.exe` 后没有任何反应

多半是当前 Python 解释器没有 tkinter。界面启动失败的原因会写在 `.ui/gui_error.log`，先看它。

```powershell
# 5 秒确认
.venv\Scripts\python.exe -c "import tkinter; print(tkinter.TkVersion)"
```

报 `ModuleNotFoundError` 就换一个带 tkinter 的解释器重建 `.venv`（见「关于 tkinter」一节）。
临时也可以走命令行：`tools\START_HERE.cmd --cli`。

若 `.ui/gui_error.log` 不存在、界面也没出现，说明连 Python 都没拉起来：
检查 `.venv\Scripts\pythonw.exe` 是否存在，以及项目根目录的 `.venv` 是否完整。

### 启动服务时报「端口无法绑定」

**最常见的原因：已经有一个服务实例在运行。** 不需要重复启动。

```powershell
# 能返回 JSON 就说明服务已在运行
curl http://127.0.0.1:6701/health
# 或直接双击 tools\查看状态.bat
```

确认没有实例却仍报错时，用 `netstat -ano | findstr :6700` 看是谁占了端口
（正常情况下只可能是本项目的 Python 进程，或 NapCat 自己的端口冲突）。

### 界面能开，但日志报 `No module named 'msgx'`

`PYTHONPATH` 没设上。双击脚本会自动设置；手动跑命令行时需要先 `set PYTHONPATH=src`，
或在项目根执行一次 `pip install -e .`。

### 界面显示「服务在跑」但「协议端未连接」

这两件事是分开的：服务起来了不等于 NapCat 连上了。

- **NapCat 根本没启动** → 点界面上的「启动协议端(NapCat)」按钮（会弹一次 UAC，点「是」）。
  该按钮的路径来自 `config.toml` 的 `[napcat] start_script`；**看不到这个按钮，就说明那一项是空的**。
- **NapCat 在跑但仍连不上** → 检查它那边的反向 WS 地址是否为
  `ws://127.0.0.1:6700/onebot/ws`（**不是** `/onebot`），端口是否为 6700。

### 服务起来了，但数据库里一条消息都没有

先看服务端窗口有没有 `协议端已连接`。

- **没有** → NapCat 没连上：先点界面上的「启动协议端(NapCat)」；若已启动，
  再检查反向 WS 地址是否为 `/onebot/ws`（不是 `/onebot`），端口是否为 6700
- **有，但没数据** → 检查 `[watch] groups` 是否限制了群号；确认小号已加入目标群

### NapCat 窗口一闪而过

见 §4.3。根因是 `launcher.bat` 用 `%cd%` 推导路径，右键管理员运行时工作目录变成了 `System32`。
用 `tools\start_napcat.bat` 启动。

### 图片全是 `[图片]` 占位，没有文字

```powershell
python -m msgx.main vision --force
```

若返回「不支持」，说明模型不接收图片输入，会降级为本地 OCR。
若 OCR 也没结果，检查 `rapidocr-onnxruntime` 是否为 `1.2.3`（1.3.x 改了返回结构）。

### 日志报 `image file is truncated` / `unsupported image`

**不是 OCR 的问题，是图片下载不完整。** NapCat 的图床偶发半途断流，半张图被写盘后
OCR 和多模态接口会先后报错 —— 两处都只是结果，根因在下载。

> 版本备注：v0.4.0 加了长度校验但**下载路径没修**（aiohttp 的 `read(n)` 是
> 「有数据就立刻返回」，每张图只拿到第一个 chunk），日志表现为恒报
> 「收到 16384 / 应为 N」然后放弃。v0.4.1 起改为读到 EOF + Pillow 校验，
> 服务启动时还会把上次误判 failed 的图片自动重新入队。

程序现在会整包读回再用 Pillow 校验可解码性，**坏图不落盘**。
若仍频繁出现，多半是网络不稳，检查代理或重连。

### 协议端断开后消息停了（日志见「协议端断开」）

QQ 会话掉线 / NapCat 进程退出后，NapCat 不会再自动重连（5s 重连只在它自己活着时有效），
而服务侧毫无异常，唯一征兆是状态卡片「协议端」变回未连接。
v0.4.1 起断开超过 60 秒会弹 P0 气泡提醒；看到提醒后点「启动协议端(NapCat)」即可。

### 界面群列表显示「(未命名) 754842541」

群名之前只能靠 `config.toml` 的 `[watch] names` 手填。v0.4.1 起协议端连上后会自动
调 `get_group_list` 拉真实群名；也可以在界面点「刷新群列表」（需服务与协议端都在线）。

### 摘要太长了 / 长度不对

纪要的长度**不是**靠提示词保证的 —— 实测模型会无视「不超过 N 字」。真正的保证在
`summarize.py` 的 `_fit_length`（分层合并 → 压缩 → 句子边界硬截断）与 `_merge_all`（分层）。
若改动了这两处或 `digest_system()` / `merge_final_rule()`，跑
`python tests/test_digest.py` 验证契约仍成立。

想改字数档位就改 `summarize.py` 顶部的 `DIGEST_RANGES`（每个范围的目标字数）与
`DIGEST_DEFAULT_CHARS`（增量默认）—— 提示词、压缩、硬截断、测试全都从这两处派生，
不要在别处硬编码字数。

### 图片语义一直是「失败」

先看界面「图片语义失败」那一项：

- 括号里写「N 张会自动补跑，最多 3 次」→ 还有救，等一会儿（空闲轮每 ≈60 秒补一批）
- 括号里写「已试满 3 次，不再重试」→ 这些图的内容读不出来了，
  可用 `sqlite3` 把 `messages.vision_tries` 归零让它重来一次

根因通常是本机到 `api.deepseek.com` 的连接抖动（本地代理撤连接，约 1/8 概率），
**与图片大小无关**（实测 13KB 与 126KB 的图都是 0 失败）。程序已有 HTTP 层重试
（默认 4 次 + **连接从不复用**，每次新建连接），若仍大面积失败，
先确认 `python -m msgx.main vision --force` 能否通过 —— 不过说明网络或模型侧有问题，
不是本项目的问题。

> v0.5.0 曾有一处**自我放大**的回归：重试前 `close()` 掉共享的会话，会**连带掐断
> 同一批并发的其它请求**，于是 1 次抖动被放大成一片失败。v0.5.1 已删除该方法并改用
> `force_close` 连接器。**改 `llm.py` 时不要重新引入「重试前重建会话」这种写法。**

v0.5.0 之前的老库请放心：启动时会自动按「有没有语义文本」回填 `vision_state`
（有文本 → `ok`，无文本但有图 → `failed`），历史失败图会全部进入可补跑集合。

### 摘要全是空的

该模型默认开启思考。如果 `llm.py` 里 `think=False` 被去掉，思考 token 会吃满预算导致正文为空。
周期摘要另有 `[summary] min_messages` 门槛（每组不足 N 条就跳过）；
**纪要不看这个门槛**，手动点按钮只要窗口内有消息就一定有产出。

### 日志报「输出被截断」（v0.5.1）

**是思考 token 把 `max_tokens` 吃光了**（思考与正文共用同一个额度）。需要思考的任务
（打分、复核）现在会自动把预算抬到 `THINK_MIN_TOKENS = 1200` 的下限；若日志里出现
「输出被截断且正文为空……放大到 N 重试一次」，说明首次预算还不够、程序已自动放大重试。
若随后又出现「放大预算后仍被截断」的 **error**，那多半不是预算问题（如被内容审核拦下），
需要看 `finish_reason`。想看更细可调 `[llm] think_min_tokens`。

> 注意：`max_tokens` 只是**上限**、不是预留，抬高它并不会多花钱 —— 模型写完了就停。

### 点了「启动协议端」什么都没发生 / 报「目录不完整」

界面默认用**隐藏模式**启动（不弹 CMD 窗口），所以启动成功时界面上确实「看不到东西」——
确认方式：看「协议端(NapCat)」那一项是否变成「已连接」（通常 10~30 秒），
以及 QQ 是否起来了。

如果弹了错误框，按提示处理：

- **「NapCat 目录不完整，缺少 …」** → `[napcat] dir` 指错了，或解压不完整。
  用 `python tools/check_napcat_env.py` 体检
- **「没能定位到 QQ.exe」** → 注册表里没有 QQ 安装记录。
  在 `[napcat]` 段直接填 `qq_path = "D:\\App\\QQ\\QQ.exe"`
- **UAC 被取消**（ShellExecuteW 返回 5）→ 重新点一次，在弹窗里选「是」

**排障时怎么看到完整输出**：设置页取消勾选「隐藏控制台窗口启动」→ 保存 → 重启服务，
再点启动按钮；或直接双击 `tools\start_napcat.bat`。
另外界面有「协议端日志」按钮，能看到启动记录（含预检结果）与 NapCat 自身日志的尾部。

> 隐藏模式下如果 `launcher.bat` 返回非 0，会弹一个消息框告诉你退出码 ——
> 这是为了避免「什么都没发生」这种最难查的失败形态。

# 消息萃取（msgx）

把指定的 QQ 群变成一份**可检索的知识流**。

实时接收 → 结构化落库 → 图片 OCR / 可选手动识别 → 每日纪要与多日归纳。

> **这个项目不会发出任何消息。** 它只读不写，从设计上就去掉了「被风控」和「打扰群友」两条路径。

## 它解决什么问题

技术群里的有效信息密度很低：一天几百上千条，真正值得看的可能只有几条，但它们和闲聊、表情包、接龙混在一起。
事后想找「上周有人提到的那个显存工具叫啥」时，聊天记录已经刷得翻不到了。

本项目的做法是：

1. **消息落库** —— 按设置过滤后保存，之后可按群、按时间、按关键词检索
2. **图片可检索** —— 有链接的图片先做本地 OCR；是否纳入摘要由用户选择，图片语义按需手动识别
3. **通过摘要阅读重点** —— 不进行单条消息评分，不发送点名、摘要或故障通知；运行情况保留在界面和日志中
4. **按自然日保存纪要** —— 每天北京时间 00:00 总结刚结束的一天；也可手动选日期补做。
   多日归纳复用已保存的每日纪要，按主题整理变化与分歧，不重复上传已有日报的聊天原文

## 架构

```
QQ 群
  │  （你在群里，机器人小号也在群里）
  ▼
官方 QQ 客户端（NTQQ）
  │  NapCat 注入 QQ 进程，把消息转成 OneBot 11 协议
  ▼
NapCat ──反向 WebSocket──► 本服务 :6700/onebot/ws
  ▲                           │
  │ 启动由界面发起             ├─► 归一化 + 去重 ──► SQLite（WAL）
  │ （隐藏窗口，无 CMD 黑框）  │
  └── msgx.napcat             ├─► 图片下载 ──► 本地 OCR / 可选手动识别 ──► 入库
                              │
                              ├─► 自动日报 / 周报 / 月报 ──► 全文页面 + HTML
                              │
                              └─► 账单（msgx.billing）──► GET /health、/billing
                                    新 API：返回 Token × 可配置费率（估算）
                                    旧版 DeepSeek：余额差值 ＋ 可选平台明细
```

**为什么用独立的机器人小号？** 因为协议端需要注入 QQ 客户端，用主号有风险。小号只用于接收（本项目从不发消息），
主号留在群里正常使用；程序不再处理点名提醒，也不发送通知。登录二维码仍会自动显示。

## v0.9.0 界面使用

- **与我相关**：实时消息底部与群活跃度、消息详情并列，按设置中的目标 QQ 识别；
  本人发言和单独 @ / 引用回复在主表标红。含 @全体成员的消息不进入相关列表。
  列表随群筛选、采用当前显示条数，但独立于主表查询；双击相关消息切换到详情。
  NapCat 对应反向 WS 连接需要开启 `reportSelfMessage`；开启前未上报的本人发言无法补回，
  没有明确 @ 且引用原消息不在库中的历史回复也无法判定。
- **自定义图标**：设置 → 程序图标 → 选择图标（PNG / ICO）。程序保存到 `.ui/app-icon.ico`，
  窗口及运行时任务栏立即使用，重开继续使用，原图片可以移走。磁盘上的 EXE 图标和已有固定快捷方式不在此设置范围。
  v0.9.2 起 ICO 原样保存，PNG 的各尺寸直接从原图生成，避免重复缩放；包含 20、24、40 像素等常用尺寸。
- **Flex 金额**：API 单价仍填写 Standard 基准价；明细显示 `flex ×0.5` 表示金额已折算，不能再除以二。

## 环境要求


| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 10 / 11 | 图形界面与 NapCat 启动器在 Windows 上使用 |
| Python | **>= 3.11** | 用到标准库 `tomllib`（3.10 及以下没有） |
| QQ（NTQQ） | **buildVersion >= 40768** | NapCat 的硬性要求。实测 `9.9.33-52230` 可用 |
| NapCat | `NapCat.Shell.zip` | 见下方安装步骤。**不要**用 OneKey 包 |

依赖只有 3 个直接包（`aiohttp` / `pillow` / `rapidocr-onnxruntime`），全部支持 pip 直接安装，
不需要 paddle、torch、Node.js。

## 快速开始

### 1. 准备环境

```powershell
# 在项目根目录执行。"py -3.13" 换成你那个带 tkinter 的解释器
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
```

`requirements.lock.txt` 是一份**实测跑通的环境快照**（21 个包，含传递依赖）。
不要用 `requirements.txt` 复现环境 —— 它只声明直接依赖，版本范围较宽。

> 如果 pip 装不上，先试默认源（很多情况下本地缓存里就有全部 wheel）；
> 换国内镜像出问题时优先怀疑镜像本身，而不是网络。

### 2. 配置 API 与安全密钥（0.7.0）

打开程序的「设置 → API 配置」，在「使用配置」中选择 OpenAI 或 DeepSeek。
两套配置独立保存，可新增自定义配置。默认选中 OpenAI 官方、`https://api.openai.com/v1`、
`gpt-6-luna`，使用 Responses 接口。服务名称、地址、模型均可修改；接口格式可选
`responses` 或 `chat_completions`，是否兼容取决于目标服务。思考强度默认 `none`。
上下文、输出上限、费率、长上下文计价规则和汇率也可编辑，换模型时按其文档调整。
DeepSeek 预填旧 `[llm]` 中的地址、模型、费率及工作日峰谷时段，修改后与 OpenAI 互不覆盖。

v0.8.7 新增「OpenAI 服务档位」：`flex` 为低价慢速，`default` 为 Standard。
官方 OpenAI 的旧配置没有此字段时默认采用 Flex，已明确保存的选择保持不变；
Chat Completions 和 Responses 的摘要及手动图片请求均适用，其他平台不发送此参数。
单价仍填 **Standard 基准价**，无需自行减半：按实际返回档位估算，Flex 自动乘 0.5。
例如 GPT-6 Luna 短上下文 Flex 输入/缓存输入/输出每百万 Token 为 $0.05/$0.005/$0.25；
长上下文倍数继续适用。依据：[模型定价](https://developers.openai.com/api/docs/models/gpt-6-luna)、
[Flex 使用说明](https://developers.openai.com/api/docs/guides/flex-processing)。
Flex 单次总等待至少 15 分钟，资源不足时有限退避重试，不自动改用 Standard；
结果未知仍需确认后补生成。未返回服务档位时，账单注明按请求档位估算，历史费用不重算。
实时消息默认显示 200 条，仍可手动修改条数。

在遮盖输入框粘贴自己的 API Key，点击「保存配置 / 替换密钥」。密钥保存在当前
Windows 用户的凭据管理器中，保存后输入框清空、只显示已配置状态。
v0.8.8 起，新输入的密钥会显示「尚未保存」；点击保存后，按钮下方显示带时间的成功或失败结果。
「新密钥已配置」仅表示本地安全保存完成，不代表已经通过付费 API 验证。
窗口顶部固定显示最近操作状态，刷新显示处理进度与结果；重复操作、取消和失败也会明确提示。
选择配置会自动保存切换；直接编辑参数后需点击保存。新任务读取最新选择，正在运行的
摘要固定使用开始时的平台、模型和费率，无需为切换 API 重启服务或 QQ。
升级代码后的首次使用仍需重新打开程序、重启本服务。不要把密钥发到聊天、配置文件或命令行。

- 「导入 / 导出 API 配置」针对当前选中的一套公开参数，示例见 `docs/api-config.example.json`，不包含密钥；含未知或密钥字段的文件会被拒绝。
- 密钥与配置标识及完整 API 基础地址绑定。同一地址的不同配置也不串用密钥，修改地址需单独配置。
- 「删除此地址密钥」只删除当前配置的密钥，阻止其后续请求；已经发出的请求仍可能完成。
- 请求仅允许 HTTPS，校验证书，不跟随重定向；错误不显示服务端原始内容，日志统一脱敏。
- Responses 使用流式响应、`store=false`，完整接收后保存摘要；流中断不自动整单重发，避免重复收费。

凭据管理器能避免配置、Git 和普通日志泄露，不能防御已控制当前 Windows 账号的恶意程序。
`store=false` 也不代表服务商完全不保留安全审计数据。
旧配置的环境变量方式仅为兼容保留；启用 `[api]` 后不读取旧版明文或环境变量密钥。
DeepSeek 第一次切换时需单独输入并保存其密钥；初版 0.7.0 已保存的 OpenAI 安全密钥继续有效。
消费明细新增「平台 / 模型」，按各自请求的费率记账，历史未记录的平台显示为「历史未记录」。

不配置也能启动，只是不会生成摘要。

## 安装 QQ 与 NapCat

这一步是整套流程里最容易卡住的地方，请按顺序来。

### 4.1 安装 QQ（NTQQ）

```powershell
winget install --id Tencent.QQ.NT -e
```

装完后确认版本：

```powershell
winget list --id Tencent.QQ.NT
```

也可从官网下载：<https://im.qq.com/pcqq/index.shtml>

> **注意**：`winget` 不一定装到默认目录（实测此机器装在了 `D:\App\QQ\`）。
> 不要猜路径，用 `winget list` 看版本即可；NapCat 会自己从注册表找 QQ。

### 4.2 下载 NapCat

从 GitHub Releases 下载 **`NapCat.Shell.zip`**：

<https://github.com/NapNeko/NapCatQQ/releases/latest>

| 包名 | 大小 | 说明 |
|---|---|---|
| **`NapCat.Shell.zip`** | ~29 MB | ✅ **用这个**。不需要额外装 Node.js |
| `NapCat.Shell.Windows.Node.zip` | ~117 MB | 自带 Node.js，没有 Node 环境时用 |
| `NapCat.Framework.zip` | ~30 MB | 需要另装 QQ 且走另一套注入方式 |
| `NapCat.Shell.Windows.OneKey.zip` | ~1 MB | ❌ **不要用**。这是个下载器，内部硬编码的下载域名已失效，必然报 404 |

解压到任意目录，例如 `D:\App\NapCat\`。解压后必须能看到这些文件：

```
NapCatWinBootMain.exe     ← 启动器实际调用的是它
NapCatWinBootHook.dll
launcher.bat
napcat.mjs
qqnt.json
```

如果缺文件，说明解压不完整，重新解压一次。

### 4.3 启动 NapCat

> ⚠️ **不要直接右键 `launcher.bat` 选「以管理员身份运行」。**
>
> `launcher.bat` 全程用 `%cd%`（当前工作目录）而不是 `%~dp0`（脚本所在目录）来推导路径。
> 右键管理员运行时，工作目录是 `C:\Windows\System32`，于是它去找
> `System32\NapCatWinBootMain.exe`，找不到就退出 —— 表现就是**窗口一闪而过**。

正确做法是先从注册表读出 QQ 的安装位置，再切到 NapCat 目录启动。本仓库提供了现成的包装脚本：

```cmd
tools\start_napcat.bat
```

它会：修正工作目录 → 自提权 → 自检关键文件 → 调用 `launcher.bat` → 出错时保留窗口以便截图。
**这条路径会留下一个命令行窗口**，是刻意保留的「看得见」模式，专供排障。

> **日常使用不用走这条。** 双击 `消息萃取.exe`，需要恢复协议端时点「强制重启」并确认 ——
> 默认**隐藏控制台窗口**，任务栏里不会留下黑框（这是 v0.5.0 专门解决的）。
> 它需要 `config.toml` 里配好 `[napcat] dir`；启动前会在 Python 侧先做预检
> （关键文件是否齐全、QQ.exe 能否从注册表推导出来），不合格就直接报错，
> 不会像批处理那样静默挂死。强制重启始终隐藏控制台；独立排障脚本保留可见输出。

启动成功后：

- 会弹出 QQ 登录界面 / 二维码（**用小号扫码登录**）；界面会自动把二维码弹出来
- WebUI 地址：<http://127.0.0.1:6099/webui/>
  登录 Token 在启动日志里，形如 `[WebUi] Login Token is xxxxxxxx`

### 4.4 让 NapCat 连上本服务

**推荐：预置配置，登录后自动连上，不用手点 WebUI。**

编辑 `NapCat目录\config\onebot11.json`（若文件不存在就新建；账号首次登录时 NapCat 会用它作全局模板）：

```json
{
  "network": {
    "httpServers": [],
    "httpSseServers": [],
    "httpClients": [],
    "websocketServers": [],
    "websocketClients": [
      {
        "name": "msgx",
        "enable": true,
        "url": "ws://127.0.0.1:6700/onebot/ws",
        "messagePostFormat": "array",
        "reportSelfMessage": false,
        "reconnectInterval": 5000,
        "token": "",
        "debug": false,
        "heartInterval": 30000,
        "verifyCertificate": true
      }
    ],
    "plugins": []
  },
  "musicSignUrl": "",
  "enableLocalFile2Url": false,
  "parseMultMsg": false,
  "imageDownloadProxy": "",
  "timeout": {
    "baseTimeout": 10000,
    "uploadSpeedKBps": 256,
    "downloadSpeedKBps": 256,
    "maxTimeout": 1800000
  }
}
```

> **路径必须是 `/onebot/ws`，不能写成 `/onebot`。**
> 本服务的 `/onebot/ws` 是 WebSocket 端点，`/onebot` 是 HTTP POST 上报端点。
> 写错会在第一次握手就失败（实测返回 HTTP 405）。

连上后，服务端窗口会出现：

```
INFO  msgx.onebot   协议端已连接: 127.0.0.1
```

## 配置

所有配置在 `config.toml`，改完重启服务生效。**没有配置的项会用内置默认值**，所以你可以只写需要覆盖的部分。

### 最常改的几项

```toml
[watch]
# 留空 = 处理机器人小号加入的全部群
groups = []
# 群号 → 群名（群消息事件不带群名，补上便于阅读）
[watch.names]
123456789 = "某个技术群"

[summary]
target_chars = 3000        # 总结后的目标字数，不是正文截取长度
prompt = ""               # 留空使用内置提示词，也可在界面设置中编辑
```

> 按北京时间自动生成日报、周报和月报；字数分别为此设置的 1、2、3 倍。旧的滚动间隔不再生效。
> 首次启用时将「昨天」记为自动补做起点，首次最多补昨天；此后因服务未运行而漏做的日期
> 会在下次启动时从该起点逐日补做。更早的历史日期需手动选择。

### 成本

新 API 根据每次响应返回的 Token 和设置中的费率估算，历史记录不按新费率重算。
默认 Luna 标准价为每百万 Token：输入 $0.10、缓存输入 $0.01、输出 $0.50。
输入超过 272,000 Token 时，默认输入 / 缓存价乘 2、输出价乘 1.5。
人民币换算默认 7.0，仅为可修改的估算汇率，不是实时汇率。
其他计费项、平台优惠和估算误差以官方账单为准；程序不查询 OpenAI 余额，充值金额需在官方平台查看。
0.7.6 起新请求保存费率、汇率、服务层级及美元估算；OpenAI 官方请求显式使用标准层级，
返回的服务层级参与估算。历史未保存的美元金额或用量显示未知，不猜测或覆盖旧金额。
OpenAI 返回的缓存写入 Token 单独按输入单价的 1.25 倍估算，不混作缓存读取或再叠加一份输入费；
旧版未记录该字段的请求不能准确回算。接口未返回缓存写量时，该项暂按 0 估算并在结果中提示，
不代表实际没有缓存写入费。这一遗漏已修复，但不能据此解释全部平台差额。
「今日消费」按北京时间统计；OpenAI 平台日账单按 UTC（UTC 00:00 对应北京 08:00），
请使用消费明细中的 UTC 日汇总与平台美元金额对照，而非相加北京日期的人民币记录。
本地请求记录可能不覆盖其他程序调用、未返回用量的失败请求或平台调整，不能保证与扣费完全一致。
参考 [模型文档](https://developers.openai.com/api/docs/models/gpt-6-luna) 与
[官方价格](https://developers.openai.com/api/docs/pricing)。

以下为**未启用新 `[api]` 配置时的旧版 DeepSeek** 账单逻辑：
按 `deepseek-flash` 价目表（2026-09-10 起生效）本地估算：

| 项目 | 空闲时段 | 高峰时段 |
|---|---|---|
| 输入 · 缓存命中 | ¥0.02 / M tok | ¥0.04 / M tok |
| 输入 · 未命中 | ¥1.00 / M tok | ¥2.00 / M tok |
| 输出 | ¥4.00 / M tok | ¥8.00 / M tok |

高峰时段为 UTC 周一至周五 `01:00-04:00` 与 `06:00-10:00`（北京时间工作日
09:00-12:00、14:00-18:00）；**周末全天按空闲计价**。倍数与时段都在 `config.toml`
的 `[llm]` 里（`peak_multiplier` / `peak_windows_utc`），官方调价时改这几行即可。

费用由摘要输入规模、手动识别的图片数量以及重试次数决定，可在「消费明细」查看每次请求。
模型调用仅用于**摘要总结和手动图片识别**；查询账单与本地 OCR 不消耗模型 Token。
启动不发送图片能力测试请求，文字消息、点名和未经手动选择的图片均不触发独立推理。

`max_daily_cost_cny` 默认 10 元，本地累计用量达到该门槛后停止新的模型调用，仍可收消息。

> **口径说明（v0.5.1 更新）**：界面上「今日花费 / 累计花费」有**三档来源**，
> 每档都会如实标注，不会混着糊弄：
>
> | 界面标注 | 数据从哪来 | 需要配什么 | 特点 |
> |---|---|---|---|
> | `（平台）` | DeepSeek 平台逐日消费明细 | 平台登录态 `userToken` | 最全，能到「逐模型」；token 短期有效 |
> | `（余额差值）` | **官方余额的下降量累加** | **什么都不用配** | 真实，但分辨率只到 ¥0.01、只给总额 |
> | `（估算）` | 官方价目表 × 本地 token 用量 | 什么都不用配 | 兜底；天然偏低 |
>
> **余额差值法（v0.5.1 新增，日常就看这个）** —— 官方 `GET /user/balance` 给的是
> **实时余额**，而账号里唯一让钱变少的事就是消费，所以「所有下降量之和」就是真实消费。
> 程序每次查余额时顺手把读数存下来（**不额外发请求**），相邻读数一减即得：
> 下降 = 消费，上升 = 充值（单记，不算消费）。**不需要 API Key 之外的任何凭据。**
>
> 它有三个诚实的边界，界面都会标出来：
> 1. **分辨率 ¥0.01**（余额只有两位小数）。日消费 ¥0.5 以上时误差约 2%；
>    某天只花几分钱时，差值就是噪声 —— 那种情况界面仍标「余额差值」，不冒充「平台」
> 2. **首次安装的那一天，「今日」会回落到估算**，并显示「自 HH:MM 起」。
>    因为读数是从启动那一刻才开始记的、只覆盖了半天，直接报出来会是个明显偏小的数
>    （用户会以为程序坏了）。**过了当晚 00:00，今日就自动变成真实值**
> 3. **累计值可能标成「（差值+估算）」**：差值只覆盖读数起始日之后，
>    更早的历史用估算补齐。刚装的那天「累计」不会显示 ¥0.00
>
> 需要「哪个模型花了多少」这种逐模型明细时，才需要配平台 token：把浏览器登录态
> 填到 `[billing] platform_token`（或界面设置页）—— 取法：浏览器登录
> platform.deepseek.com → F12 → Application → Local Storage → 复制 `userToken` 的值。
> token 只存在本机 `.ui/preferences.json`，不会进 Git。
>
> **两套凭证互不通用**（这点最容易搞混）：API Key（`sk-…`）只能查**余额**；
> 消费明细只有平台登录态能查。用 API Key 打用量接口会返回
> `code=40003 Authorization Failed`。所以本项目的策略是：**余额用 API Key 自动查，
> 消费从余额差值推**——两者都不需要你额外做任何事。
>
> 本地估算天然偏低，原因是**重试后实际被服务端处理、但我们没拿到响应体的那些请求
> 无法计数**（见「图片语义提取」一节的连接抖动）。这就是为什么 v0.5.1 要用差值法
> 取而代之。

**务必注意**：该模型默认开启思考模式，思考 token 与正文共用 `max_tokens` 且按输出价计费。
本项目对「摘要、图片描述」这类忠实提取任务已显式关闭思考（`think=False`），
实测同一任务从 1500 token 降到 34 token —— 约 **9 倍**差距。改动 `llm.py` 时不要把这个开关去掉。

摘要 HTML 输出在 `data/reports/YYYYMMDD/`，可直接双击用浏览器打开。
「摘要全文」页左侧按内容所属日期倒序显示摘要，打开界面默认读取内容日期最新一份；点击列表即可在右侧阅读正文。
0.8.4 起，日／周／月报告按覆盖结束时间倒序，同一结束时间按起始时间倒序；
只有相同窗口才以生成时间和记录 ID 区分先后。旧日期补生成不会被排到较新日期前面，排序后取最近 50 份。
0.8.1 起列表仅显示日报、周报、月报，可筛选全部或其中一类，均标明完整起止日期。
其他旧版摘要只隐藏、不删除。消息服务未启动时也能查看历史。
主题目录可跳转正文，较大的字号、行距和淡色主题块方便阅读；没有小标题的内容保留普通段落。
历史阅读及排版只读取本地数据，不重新请求模型、不增加 Token 消费；完整正文仍可复制或打开 HTML 文件。
阅读状态由用户手动选择：未读白色、粗读黄色、深读绿色，打开文章不会自动标记已读。
选中正文后可添加下划线、蓝色一般重点或红色特别重点，也可清除；三类报告均可保存心得。
阅读状态和批注保存在本地数据库，不修改原文及既有 HTML；重新生成的日报是新版本，默认未读，不自动移植旧批注。
周报、月报优先参考红色特别重点，其次蓝色重点，并把心得明确作为个人观点。
月报还补入完整周报内各日报的最新重点和心得，因此周报生成后才写下的心得不会漏掉。
标注和保存不调用模型；生成上级报告时这些附加文字才增加输入 Token。已完成报告直接复用，
之后新增标注不会自动重写已完成的周报或月报。

自动计划均使用北京时间、左闭右开的完整自然周期：

| 类型 | 触发时间 | 材料 | 篇幅 |
|---|---|---|---|
| 日报 | 每天 00:00 | 前一天聊天正文及已勾选的图片文字 | 日报设置 D |
| 周报 | 每周一 00:00 | 上周一至本周一的日报 | 2D |
| 月报 | 每月 1 日 00:00 | 上月内完整周报＋月初、月末的对应日报 | 3D |

午夜先等待约 30 秒让已收到的消息入库，再按日报→周报→月报顺序提交，生成完成时间取决于模型响应。
月报不使用跨月周报，避免混入邻月内容。缺少的下层报告先补齐，已有结果不重复请求模型；空周期不请求模型。
初次启用周、月计划的基线固定为当前周一、当前月初；升级保留原有日报补做基线。
为完成首个月报，必要时会补齐当月较早的日报和完整周报，会产生相应模型费用；不独立回补此前月份。
电脑或服务关闭时无法生成，重新启动消息服务后按保存基线补做漏掉的完整周期。
网络未连接或明确临时拒绝时有限重试；周期任务最多尝试 3 轮，轮间至少 30 分钟。
输出截断、处理结果不明或永久错误会停止该任务自动重试并显示原因，其依赖报告等待处理，不冒充完整汇总。
摘要是有损压缩，周报和月报无法恢复下层报告未保留的细节。

### 运行状态

- **状态卡片**（两列并排）：
  - 左列：服务进程 / 已入库消息 / **今日花费** / 账户余额
  - 右列：协议端（NapCat）连接 / **累计花费**；模型状态单列显示
  - 启动服务、停止服务和强制重启放在服务状态栏，刷新账单及官方平台入口放在账户余额旁。
  - 「今日花费」右边紧挨着「累计花费」—— 两个都是**钱**，必须能一眼对比。
    每个金额都带**口径标注**：`（平台）` = 平台逐日明细、`（余额差值）` = 官方余额
    下降量推算的真实值（默认就有，无需配置）、`（估算）` = 本地按 token 用量算的兜底值、
    `（差值+估算）` = 累计里「读数起点之前」那一段用估算补齐。**今日与累计各自标各的**，
    可能一个是真实、一个是估算。拿不到的原因会写在底部状态栏
    （**绝不把估算值伪装成真实值**）。
    今日用差值口径但读数起点不是 00:00 时，会显示「自 HH:MM 起」（首次安装那天就是如此；
    过了午夜自动变成完整一天）。
  - 「协议端」一项会明确区分 *服务在跑* 和 *NapCat 已连上* —— 这两件事经常被混淆，

  - 新报告到达时刷新阅读列表，保留当前文章、滚动位置、选文和心得，不打断阅读。

    估算金额和结果，并按用途与消息类型统计全部记录。选中请求可以查看关联消息原文。
    Token 来自 API 返回，费用按配置费率估算；无用量的请求显示未知，升级前费用单列为历史未归因。
    仅显示「摘要总结」「图片理解」；旧评分、固定分块、旧合并用途隐藏，历史账目保留。
    超过上下文时的必要分块及合并同样计入「摘要总结」。
    「总金额」累计所选用途的全部记录，「今日消费」按北京时间当天零点到次日零点统计。

    底部默认显示最近 30 天消费折线图：摘要总结与图片理解分别着色，按北京时间及人民币本地估算统计，

  `cache/qrcode.png` 就完事了，从不负责展示 —— 界面会盯着那个目录，

  每份最多 2 MiB，保留 3 份轮转备份；界面启动、停止和协议操作记录见 `data/logs/gui.log`。

  几个 QQ.exe —— 重复启动一眼可见；每 2 秒自动刷新），**不用再点按钮弹窗口**。
  日志按行上色：**白 = 平常，绿 = 在收消息/链路正常（协议端已连入、消息入库），
  红 = 出问题了（WARNING/ERROR/失败/断开不再入库）**。
  判定先红后绿 —— 同一行两个词都出现时，出问题必须压过一切。

> 服务与协议端是**两个独立进程**：本服务只负责监听协议端连入，不负责启动它

- 底部「群活跃度」按北京时间今日 00:00 至次日 00:00 的消息时间统计本地入库的未过滤消息，按数量降序。
  点击群直接筛选上方消息；统计不受显示条数、当前群或图片筛选影响。
  0.8.5 起不计入已保存的过滤图片、表情包，即使已完成 OCR、图片识别或勾选「纳入摘要」也不计数。
  最近消息时间同样只取未过滤消息；当天仅有过滤消息的群显示 0 条、最近消息为「—」。
  过滤图片仍可查看和手动纳入摘要。同一条未过滤消息多张图或被多个账号接收只计一次；不代表 QQ 全部实际消息量。
- 每 3 秒自动刷新（可关闭），**只在切到该页时才拉数据**，后台页不会浪费请求

这一页是为了替代「盯着 NapCat 那个 CMD 窗口看消息到底进没进来」——
看得见的是入库后的真实内容，比协议端滚屏有用得多。

点「停止服务」时不会强杀进程，而是发一个信号文件让服务自己收尾退出 ——
这样不会打断正在写数据库或下载图片的动作。

### 群消息纪要（默认摘要形态）

自动计划通过所配置的模型 API 生成**会议纪要**：一个总标题、若干独立主题段，
每段有**加粗小标题**，交代「发生了什么、结论是什么」。

发送材料只包含聊天正文及已有图片文字，按消息时间升序、同秒按入库编号排序。
不逐条发送群名、发言人、时间、类型包装或统计范围说明；设置中的系统提示词仍保留。
逐图采用已勾选的图片理解结果，没有时才使用该图已有 OCR；被过滤的纯图也可只凭 OCR 手动纳入。
摘要阶段不重新解析图片。

- **按周期**：日／周／月均自动生成。日报读取原始消息，周报读取日报，月报使用月内完整周报和边界日报。
- **篇幅设置**：

  | 范围 | 目标字数 |
  |---|---|
  | 单日 | 使用已保存设置，默认 3000 字 |
  | 周报 | 日报设置的 2 倍 |
  | 月报 | 日报设置的 3 倍 |

  0.7.6 起单日不再把 2000 等较低设置抬到 3000。篇幅统计包含总标题、小标题和正文的可见字符，
  不计空白及 Markdown 格式符号；信息不足时允许更短，不编造内容凑字数。
- **提示词可编辑**：设置中预填按申论方式概括材料的提示词，强调关键词、关键句、事实与分歧，
  按主题归纳。`{{目标字数}}` 在请求时替换为对应周期字数，保存后从下一次自动生成生效。
- **上下文允许时一次提交**：读取窗口内未过滤消息及手动纳入的过滤图片，不再按固定 6000 字分块，
  不重复解析图片。只有预估输入加回答预留超过模型上下文容量时才分块，并在日志说明原因。
- **输出预算自动估算**：根据目标字数预估回答 Token 并留出余量，结合模型输出上限与剩余上下文设置
  `max_tokens`，思考强度使用 API 设置。输出 Token 预算不同于可见字数限制；请求强调在所设篇幅内完整结束，
  本地不截断正文。
  模型仍可能超过提示词指定篇幅，当前会保留完整结果并记录超长警告，不把篇幅提示当作精确字符保证。
  模型完整返回后直接保存并显示；输出未完成会明确标记失败，不冒充完整摘要。
  当前默认约 3000 字对应 10240 个输出 Token；输入 Token 使用本地保守估算，并非服务端精确分词。
- **失败保留结果**：未完成的正文单独保存在报告目录的 `unfinished/`，不推进摘要游标。
  确有超限分块时，成功的中间结果缓存于 `.summary-cache/`，只复用输入与设置一致的结果，
  不自动追加请求续写；结果不明的周期暂停，等待核查。

### 图片语义提取

接收的有链接图片先下载（校验完整性、去重）并运行本地 OCR，包括纯图片与表情包过滤记录；Q群管家的新消息直接丢弃。
此过程不调用模型。需要语义时，在「实时消息」页对指定图片点「□ 识别」；同一张已成功识别的图重复点击会复用结果。
「纳入摘要」与识别操作分开，默认不勾选：勾选后可直接发送 OCR；有手动识别语义时优先发送语义。
取消后不发送该图的语义或 OCR，已保存的识别内容仍可查看。过滤图片同样可只凭 OCR 手动纳入。
模型失败不会在后台自动补跑；可在界面重试。
图片请求使用现有的压图、有限 HTTP 重试和安全日志机制；「消费明细」记录实际模型请求费用。

### 设置

| 界面项 | 作用 | 落到哪里 |
|---|---|---|
| 摘要提示词 | 可编辑多行提示词，可恢复默认；下一次自动生成生效 | `summary.prompt` |
| 目标字数 | 日报篇幅上限 D，默认 3000 字；周报 2D，月报 3D | `summary.target_chars` |
| 统计哪些群 | 勾选参与统计的群；**不选 = 全部群** | `watch.groups` |
| 不接收的消息类型 | 纯表情 / 纯图片 / 合并转发 / 语音 / 短于 N 字 | `filters` |
| 过滤发言人 | 添加名称、删除选中项，默认 Q群管家 / 智能客服，适用于所有群 | `filters.blocked_senders` |
| 隐藏控制台窗口启动 | 启动协议端时不出现 CMD 窗口（取消勾选 = 可见排障模式） | `napcat.hidden` |
| 平台 token | DeepSeek 平台登录态，用于抓**逐模型**消费明细（**留空也不影响**：今日/累计仍由余额差值法给出真实值） | `billing.platform_token` |

设置页是**可滚动**的：窗口在小屏上被压扁时，滚轮（或拖动右侧滚动条）即可看到底部的
「保存设置」，不需要把窗口拉大。

**过滤发言人**：输入实时列表显示的完整名称 →「添加」→「保存设置」→ 停止并重新启动消息服务。
按完整名称匹配，不匹配正文或昵称子串；Q群管家在名单内时也匹配已核验的账号，删除该项即可关闭此规则。
名单允许清空。命中的新消息直接丢弃，不入库、不进行 OCR 或 LLM；历史记录保留，但从实时列表、
今日群计数、活跃排名和后续原始消息摘要输入中排除，待处理图片也暂停 OCR。
移出名单并重启服务后，已有记录恢复；此前直接丢弃的新消息无法补回。已生成摘要不自动改写。

**设置保存在 `.ui/preferences.json`（本人本地，不入版本库），界面永远不会改写 `config.toml`。**
这样配置文件的改动归版本管理，各人的偏好互不干扰 —— 多人协作时不会因为谁改了配置而互相覆盖。

规则是「留空 = 沿用 `config.toml`」而不是「清空」：比如关键词留空，服务仍会用配置文件里的关键词。

> ⚠️ **注意**：这些设置只在**从图形界面启动服务**时生效（界面通过环境变量 `MSGX_PREFS` 传给服务进程）。
> 若改用 `tools\启动服务.bat` 或命令行手动启动，服务只读 `config.toml`，**界面里的设置不会生效**。

### 重新打包 `消息萃取.exe`

只在 `tools\exe_main.py` 本身需要改动时才要重打包（业务代码改动不需要）：

```powershell
.venv\Scripts\python.exe -m PyInstaller --onefile --noconsole `
  --name msgx_launcher --distpath . --workpath build\tmp --specpath build `
  --paths src tools\exe_main.py
# 然后把生成的 msgx_launcher.exe 改名为 消息萃取.exe
```

> 「不选任何群」和「选了全部群」效果相同，都表示关注全部群。

## 排障

### 双击 `消息萃取.exe` 后没有任何反应

多半是当前 Python 解释器没有 tkinter。界面启动失败的原因会写在 `.ui/gui_error.log`，先看它。

```powershell
# 5 秒确认
.venv\Scripts\python.exe -c "import tkinter; print(tkinter.TkVersion)"
```

报 `ModuleNotFoundError` 就换一个带 tkinter 的解释器重建 `.venv`（见「关于 tkinter」一节）。
临时也可以走命令行：`tools\START_HERE.cmd --cli`。

若 `.ui/gui_error.log` 不存在、界面也没出现，说明连 Python 都没拉起来：
检查 `.venv\Scripts\pythonw.exe` 是否存在，以及项目根目录的 `.venv` 是否完整。

### 启动服务时报「端口无法绑定」

**最常见的原因：已经有一个服务实例在运行。** 不需要重复启动。

```powershell
# 能返回 JSON 就说明服务已在运行
curl http://127.0.0.1:6701/health
# 或直接双击 tools\查看状态.bat
```

确认没有实例却仍报错时，用 `netstat -ano | findstr :6700` 看是谁占了端口
（正常情况下只可能是本项目的 Python 进程，或 NapCat 自己的端口冲突）。

### 界面能开，但日志报 `No module named 'msgx'`

`PYTHONPATH` 没设上。双击脚本会自动设置；手动跑命令行时需要先 `set PYTHONPATH=src`，
或在项目根执行一次 `pip install -e .`。

### 界面显示「服务在跑」但「协议端未连接」

这两件事是分开的：服务起来了不等于 NapCat 连上了。

- **NapCat 根本没启动** → 可用 `tools\start_napcat.bat` 启动并查看输出；
  若需清理并重启现有协议实例，点界面「强制重启」并确认。
- **NapCat 在跑但仍连不上** → 检查它那边的反向 WS 地址是否为
  `ws://127.0.0.1:6700/onebot/ws`（**不是** `/onebot`），端口是否为 6700。

### 服务起来了，但数据库里一条消息都没有

先看服务端窗口有没有 `协议端已连接`。

- **没有** → NapCat 没连上：先确认协议端已启动；若已启动，
  再检查反向 WS 地址是否为 `/onebot/ws`（不是 `/onebot`），端口是否为 6700
- **有，但没数据** → 检查 `[watch] groups` 是否限制了群号；确认小号已加入目标群

### 消息好像冻结了 / 实时消息页不再更新

**先跑这一条命令**，它会自己按顺序排除，并给出「结论 + 处置」：

```powershell
python tools\diagnose_freeze.py
```

它依次看：进程归属（注入器几份、`QQ.exe` 是不是全由注入器拉起）、
连接条数、**队列探针**（往 `/onebot` 发一条固定 id 的事件，看 `received` 涨不涨 ——
这一步能区分「事件没从协议端出来」和「事件进了队列但没人取」）、
二维码是否在刷新、数据库最后一条消息的时间。约 10 秒出结果。

想自己对照着看时，按这个顺序，先确认状态再决定是否重启：

| 看哪里 | 正常 | 说明什么 |
|---|---|---|
| 运行状态页「协议端(NapCat)」 | 已连接 | 已连接**也可能没有消息** —— 见下 |
| 实时消息页「更新于 HH:MM:SS」 | 时间在走 | 时间不动 = 界面与服务失联，不是消息的问题 |
| 日志 → 协议端日志 →「当前进程」 | 注入器 1 个 | **≥2 个 = 之前连点过，先全部关掉** |
| `http://127.0.0.1:6701/health` | `ws_conns` 与 `ws_peers` 个数相等 | **`ws_conns` 更大 = 有重复实例在连** |
| `python -m msgx.main stats` | `received` 在增长 | `received` 长时间为 0 就是真的没事件进来 |

> ⚠️ `ws_peers` 是**去重后的 IP 集合**：多份 NapCat 都从 `127.0.0.1` 连进来时
> 它也只有一个元素，看起来和「1 份正常连接」一模一样。**要看 `ws_conns`（连接条数）。**
> 这是 v0.5.2 那次「消息冻结」最费时间的一个盲点。

最常见的形态是：**状态显示「已连接」，消息却停了** —— 这多半是 **QQ 登录态掉了**，
NapCat 退回「等扫码」。确认方法：看 `<NapCat 目录>\cache\qrcode.png` 的修改时间，
如果它**刚刚还在刷新**，就说明协议端正停在扫码界面等你扫码。

**处置：二维码窗口出现时先扫码；无法恢复时再确认执行「强制重启」**。
界面中的手动重启与后台凭据恢复是两条独立流程：

```
点「强制重启」并确认
  → 消息接收服务启动，检查目标账号与 HTTP / WebSocket 端口
  → 弹 UAC，点「是」
  → 定向退出该安装目录的 NapCat 进程，本次跳过快速登录
  → 重新启动并获取新二维码 → 扫码 → 收到目标账号新消息后确认恢复
```

> 遗留 `tools\重启协议端.bat` 仍是全退脚本，会关闭普通 QQ；界面不再使用它。
> 自动恢复依赖 QQ 凭证仍然有效，不能保证账号被撤销登录后总能免扫码恢复。

若协议日志报 `ECONNREFUSED 127.0.0.1:6700`，表示连接本机接收端失败，应先检查消息服务。
打开界面本身不会自动启动接收服务；可点「启动服务」，需要重新扫码时再用「强制重启」。

只想看有多少实例、不动手（**读数为 0/1 才正常，≥2 说明连点过**）：

```powershell
python tools\kill_dup_napcat.py            # 只看不动
python tools\kill_dup_napcat.py --elevate  # 只清场，不重启（之后需自行启动协议端）
```

（也可以在管理员终端里用 `--yes`，或直接到任务管理器结束**所有**
`NapCatWinBootMain.exe` 与 `QQ.exe` —— 但顺序要紧：脚本会**先杀注入器再杀 QQ**，
反过来的话注入器还活着会把 QQ 重新拉起来。）

> 正常状态下 `QQ.exe` 本来就有 **3~4 个**（1 主进程 + 渲染/GPU 等辅助进程），
> 只有 `NapCatWinBootMain.exe` 的个数才有诊断意义（0 = 没启动过 / 1 = 正常 / ≥2 = 连点过）。
> ⚠️ **<NapCat 目录>\logs\ 空着是常态**，不是故障：NapCat 4.x 默认不落盘，
> 而且 `fileLog` 是**账号级**配置 —— 只改 `config\napcat.json` 不算数，
> 每个账号的 `config\napcat_<uin>.json` 里还有一份，**优先级更高**，两份都要改，
> 且**改完必须重启协议端**才生效。

> 看门狗只检查当前登录账号：协议端连着、此前已收到该账号真实消息、该账号消息库与接入
> 均超过 30 分钟无新消息、该时段历史上本应活跃时，界面显示「疑似停止接收消息」。
> 当前账号、自动登录账号和可用缓存凭证一致时，仅重建 NapCat 登录进程，不关闭普通 QQ。
> 每次停收至多恢复一次，一小时内不重复；收到当前连接上的新消息才确认恢复。
> 无凭证或恢复后仍无新消息时保留异常状态，需要手动登录；不发送通知或调用模型。
> 二维码过期可点扫码窗口中的「刷新二维码」，只更新 NapCat 登录码，不结束普通 QQ。
> 见 `config.toml` 的 `[watchdog]`。

### NapCat 窗口一闪而过

见 §4.3。根因是 `launcher.bat` 用 `%cd%` 推导路径，右键管理员运行时工作目录变成了 `System32`。
用 `tools\start_napcat.bat` 启动。

### 图片全是 `[图片]` 占位，没有文字

已有 OCR 会直接跟在内容列的 `[图片]` 后，点击该行可在底部「消息详情」查看全文；有链接的图片都会尝试下载和本地 OCR，
但不会自动调用模型。需要图片语义时手动点击「□ 识别」。若 OCR 长期为空，检查
`rapidocr-onnxruntime` 是否为 `1.2.3`（1.3.x 改了返回结构）。不再提供收费探测命令。

### 日志报 `image file is truncated` / `unsupported image`

**不是 OCR 的问题，是图片下载不完整。** NapCat 的图床偶发半途断流，半张图被写盘后
OCR 和多模态接口会先后报错 —— 两处都只是结果，根因在下载。

> 版本备注：v0.4.0 加了长度校验但**下载路径没修**（aiohttp 的 `read(n)` 是
> 「有数据就立刻返回」，每张图只拿到第一个 chunk），日志表现为恒报
> 「收到 16384 / 应为 N」然后放弃。v0.4.1 起改为读到 EOF + Pillow 校验，
> 服务启动时还会把上次误判 failed 的图片自动重新入队。

程序现在会整包读回再用 Pillow 校验可解码性，**坏图不落盘**。
若仍频繁出现，多半是网络不稳，检查代理或重连。

### 协议端断开后消息停了（日志见「协议端断开」）

QQ 会话掉线 / NapCat 进程退出后，NapCat 不会再自动重连（5s 重连只在它自己活着时有效），
而服务侧毫无异常，唯一征兆是状态卡片「协议端」变回未连接。
状态页区分「连接中断」「QQ 已离线」「QQ 登录失效」。普通连接中断由 NapCat 按其已有配置
自动重连，不必再启动一份协议端。若最新协议日志出现 `KickedOffLine`，表示 QQ 登录被撤销，
此时本地 WebSocket 重连无法恢复收消息，需要点「重新扫码」完成手机授权。
有新二维码时直接展示；二维码过期则进入带确认的协议端重置流程。
程序不会自动反复强杀 QQ，不恢复桌面通知，也不能保证 QQ 服务端不再使登录失效。

### 界面群列表显示「(未命名) 754842541」

群名之前只能靠 `config.toml` 的 `[watch] names` 手填。v0.4.1 起协议端连上后会自动
调 `get_group_list` 拉真实群名；也可以在界面点「刷新群列表」（需服务与协议端都在线）。

### 群列表里混进了别的账号的群（下拉框里全是无关的群）

**症状**：设置页「统计哪些群」里塞了几十个从没收到过消息的群 —— 学校群、课程群、
亲戚群之类。用户的原话是「群列表太多了」。

**根因**：`groups` 表是**历次登录的并集**。协议端每换一个 QQ 登进来，
它的 `get_group_list` 就会把那个账号的全部群写进同一个表；
v0.5.4 之前这张表**连「这个群属于哪个账号」都没记**，所以分不清谁是谁。
一次误登录就会灌进来几十个空群。

**处置**（二选一）：

| 方式 | 前提 | 做什么 |
|---|---|---|
| 界面「只保留当前账号的群」 | 服务 + 协议端都在线 | 问协议端「现在登录的是哪个账号」，删掉**不属于它且没有消息**的群 |
| `python tools\prune_groups.py --apply` | 无（离线可用） | 按「有没有消息」判定 —— 服务没在跑时用它 |

```powershell
python tools\prune_groups.py                 # 默认 dry run：只打印会删什么
python tools\prune_groups.py --apply         # 真删（先自动备份整个库到 data\backup\）
python tools\prune_groups.py --keep 123,456  # 额外保住的群号
```

> **有消息的群一律不删**，保留已有群记录与消息之间的关联。
> 删的只是「群列表里的条目」，**任何消息数据都不受影响**。
>
> 界面上的群列表会标出「⚠ 非当前账号」；状态栏会写明当前协议端账号。
> 属主为空表示**未知**（v0.5.4 之前的老数据），不会被当成「别人的群」而误标。

### 摘要太长了 / 长度不对

默认单日篇幅为 3000 字；修改后以已保存设置为准，2000 字不会再被抬到 3000。
输出 Token 上限保留冗余，不能直接等同于中文字符数；请求另行明确可见字数上限，本地不硬截断。
模型超长时显示实际字数并保留完整结果，日志注明超过所设篇幅；提示词不能提供严格字数保证。
在「设置」修改目标字数和摘要提示词后保存，下一次生成就会使用新设置；既有报告不自动重写。
修改摘要实现后，运行 `python tests/test_digest.py` 检查完整输出和失败行为。

### 图片语义一直是「失败」

运行状态不再显示该计数。请查看服务日志中的图片识别记录，并在「实时消息」页按需重试。
「消费明细」可查看图片理解请求的次数、Token 和费用。
图片理解的输出上限为 2000 Token；仅手动选择时调用解析，不增加能力探测请求。

仅凭 `ServerDisconnectedError` 不能确定是代理还是服务端关闭连接。程序保留有限的 HTTP 层重试
（默认 4 次，每次新建连接），并对大请求控制上传节奏，见下方排查说明。若仍大面积失败，
查看服务日志中实际图片请求的错误及「消费明细」；不再为了排障额外发送收费测试图片。

> v0.5.0 曾有一处**自我放大**的回归：重试前 `close()` 掉共享的会话，会**连带掐断
> 同一批并发的其它请求**，于是 1 次抖动被放大成一片失败。v0.5.1 已删除该方法并改用
> `force_close` 连接器。**改 `llm.py` 时不要重新引入「重试前重建会话」这种写法。**

v0.5.0 之前的老库启动时会按「有没有语义文本」回填 `vision_state`。
旧版过滤记录若没保存图片链接，无法恢复原图；已有图片解析保留在数据库中。

### 摘要全是空的

该模型默认开启思考。如果 `llm.py` 里 `think=False` 被去掉，思考 token 会吃满预算导致正文为空。
纪要没有每群最少消息数门槛，但窗口内没有有效信息时不会强行生成内容。

### 日志报「输出未完成」

摘要请求会自动预估输出预算并留出余量；如果仍达到上限，会明确报错，不冒充完整摘要。
可在「消费明细」检查该次请求状态，已收到的正文另存于报告目录的 `unfinished/`。
该周期会停止自动重试，依赖它的上级报告等待处理。先核对消费记录及输出额度，避免重复提交可能已计费的请求。

### 日报连接中断或已停止重试（v0.8.6）

OpenAI 官方摘要采用流式响应；总等待时限至少 10 分钟，连接上限 30 秒、连续无数据上限 3 分钟。
这能减少非流式长等待，但不能保证代理或网络永不断开。只在收到完整结束标志后接受摘要，缺失用量仍标为未知。
日志会标明异常类型、请求阶段、耗时及已收到的请求 ID，不输出原始错误正文或密钥。
流式用量规则依据 [OpenAI 官方文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)。

重开新版程序并重新启动消息服务后，在「运行状态 → 自动日报 / 周报 / 月报」选择待处理日期，点击「确认补生成」。
确认框提示可能重复收费；只有确认后才重新排队，已有完整成稿直接复用。补齐后自动继续依赖它的周报和月报。
重复点击或旧的失败记录不能重复排队；若本次再次出现结果不明的中断，会重新停止，需核对后再次确认。
明确连接未建立或临时拒绝仍有有限自动重试；不能把服务器未返回用量解释成没有收费。

### 大摘要报 `ServerDisconnectedError`

本机实测：约 452 KiB 的相同请求一次性上传时在 15～20 秒断连，控制上传节奏后正常返回。
v0.6.1 已让超过 64 KiB 的请求在同一个 HTTP 请求内按 8 KiB、间隔 10ms 上传；
所有消息仍作为一个完整 JSON 交给模型，不增加模型调用，也不改网络配置。

日志会分别记录上传开始、正文提交、收到响应头，并区分连接未建立和处理结果不明的中断。
这与 `finish_reason=length`（输出额度耗尽）不同，也不能单凭断连认定是哪一段网络设备出了问题。
真实界面已验证 1516 条消息一次提交并生成完整摘要，耗时约 12 秒。

### 重启协议端无反应 / 报「目录不完整」

界面默认用**隐藏模式**启动（不弹 CMD 窗口），所以启动成功时界面上确实「看不到东西」——
确认方式：看「协议端(NapCat)」那一项是否变成「已连接」（通常 10~30 秒），
以及 QQ 是否起来了。

如果日志提示错误，按以下方式处理：

- **「NapCat 目录不完整，缺少 …」** → `[napcat] dir` 指错了，或解压不完整。
  用 `python tools/check_napcat_env.py` 体检
- **「没能定位到 QQ.exe」** → 注册表里没有 QQ 安装记录。
  在 `[napcat]` 段直接填 `qq_path = "D:\\App\\QQ\\QQ.exe"`
- **UAC 被取消**（ShellExecuteW 返回 5）→ 重新点一次，在弹窗里选「是」

**排障时怎么看到完整输出**：设置页取消勾选「隐藏控制台窗口启动」→ 保存 → 重启服务，
再按需重启协议端；或直接双击 `tools\start_napcat.bat`。
另外界面「日志」下拉切到「协议端日志」，能看到启动记录（含预检结果）与 NapCat 自身日志的尾部（每 2 秒自动刷新）。

> 隐藏启动的失败原因在协议端日志中查看；程序不再弹出故障通知。
> 界面启动失败时查看 `.ui/gui_error.log`，启动器失败时查看 `.ui/exe_error.log`。

### 一键体检

```powershell
python tools/check_napcat_env.py            # 静态检查
python tools/check_napcat_env.py --probe    # 附带端口连通性探测
```

检查项：QQ 安装与版本、NapCat 文件完整性、`onebot11.json` 配置正确性、端口占用。
